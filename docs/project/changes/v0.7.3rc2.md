# v0.7.3rc2

**Date:** 2026-09-15

---

## Summary

Release candidate fixes two schema drift bugs in the project import
(`import_project`) logic and adds a hard version guard that refuses to
merge projects of different `PROJECT_VERSION`. The import mixin had fallen
out of sync with `schema.py` after migrations 0.2.0, 0.7.1, and 0.7.2 —
columns added to `protein` and `identification` were never added to the
bulk `INSERT INTO ... SELECT FROM src.<tbl>` statements, so those fields
were silently lost during merge.

---

## Fixes

### Import mixin: missing columns in `protein` (regression since v0.2.0)

The `protein` bulk insert in `ImportProjectMixin.import_project()` copied
only 7 of 9 columns. The fields `taxon_id` and `organism_name` (added by
migration 0.2.0 / `CREATE_TABLE protein`) were dropped on import —
imported proteins had NULL taxonomy data even when the source project had
it.

**File:** `dasmixer-core/src/dasmixer/api/project/mixins/import_project_mixin.py`  
**Section:** Step 4.1 — `INSERT OR IGNORE INTO protein ... SELECT ... FROM src.protein`  
Both the INSERT-column list and SELECT-column list now include
`taxon_id, organism_name`, matching `schema.py` exactly.

### Import mixin: missing columns in `identification` (regression since v0.7.1/0.7.2)

Five columns added to `identification` by migrations 0.7.1 and 0.7.2 were
absent from the bulk insert:

- `quality` (0.7.1)
- `override_pepmass` (0.7.1)
- `has_ptm` (0.7.1)
- `lcrr` (0.7.2)
- `unconfirmed_ptms` (0.7.2)

After import, these fields were reset to NULL on every merged
identification, silently discarding PPM/coverage/quality metrics computed
in the source project.

**File:** `dasmixer-core/src/dasmixer/api/project/mixins/import_project_mixin.py`  
**Section:** Step 4.5 — `INSERT INTO identification ... SELECT ... FROM src.identification`  
INSERT-column list and SELECT-column list now include the five columns,
positioned between `isotope_offset` and `src_file_protein_id` (same order
as in `schema.py`).

## Core Changes

### Version guard for project import

A hard check is now performed at the very start of `import_project()`
(before any PRAGMA tuning or `BEGIN`) that compares the source project's
`project_metadata.version` with the target's. If they differ,
`ProjectImportError` is raised immediately:

```
Version conflict! Cannot merge project v0.7.1 into project v0.7.2.
Upgrade the source project to v0.7.2 and retry.
```

The message names the older side (`source` or `target`) and the target
version to upgrade to. The check uses the existing `_version_lt` /
`_version_gt` helpers from `dasmixer.api.project.migrations`, so version
parsing is consistent with the migration system.

**Rationale:** the column-drift bugs above exist precisely because
`import_project_mixin.py` is a hand-maintained mirror of `schema.py`.
Allowing merges across `PROJECT_VERSION` boundaries would silently
produce partial rows. The guard makes such attempts fail loudly with an
actionable instruction (open the older project first so
`apply_migrations()` upgrades it, then retry the merge).

**New exception class:** `ProjectImportError(DasmixerException)` in
`import_project_mixin.py` (re-uses the existing
`dasmixer.utils.exceptions.DasmixerException` base, same as
`MigrationError`).

**File:** `dasmixer-core/src/dasmixer/api/project/mixins/import_project_mixin.py`

## GUI / CLI

No code changes were required in the GUI or CLI callers: both already
catch the generic `Exception` from `import_project()` and surface the
message to the user.

- **GUI** (`dasmixer-gui/.../app.py`, `merge_project`): the existing
  `_show_error(f"Error merging project: {ex}")` handler now displays the
  full version-conflict message in the red snack bar.
- **CLI** (`dasmixer-cli/.../commands/import_project.py`): the existing
  `typer.echo(f"Error during import: {e}", err=True)` prints the message
  to stderr and exits with code 1.

## Docs

### AGENTS.md — new rule 15

Added "Schema changes must be synced to `import_project_mixin.py`" as
Development Rule 15. The rule enumerates:

- Per-table column lists for bulk-inserted tables (`protein`,
  `spectre_file`, `spectre`, `identification_file`, `identification`,
  `peptide_match`, `protein_identification_result`,
  `protein_quantification_result`, `generated_reports`, `saved_plots`)
  must be updated in both INSERT and SELECT clauses when columns change.
- List-inserted tables (`subset`, `tool`, `sample`) must be updated in
  their `INSERT INTO ... VALUES (...)` loops.
- New tables with autoincrement `id` must be added to the `bulk_tables`
  list (Step 4) and to the "Reset autoincrement sequences" loop (Step 6).
- The version guard (`ProjectImportError` on version mismatch) must be
  preserved — it exists specifically to prevent the column drift that
  this release fixes.

## Notes

- **No database migration:** `PROJECT_VERSION` stays at `0.7.2`. The
  fixes only correct SQL statements that copy data between two
  same-version databases; they do not change the on-disk schema.
- **`report_parameters` table is intentionally not imported:** this
  table stores GUI-side report parameter presets and was excluded from
  the import mixin on purpose. It is not affected by this fix.
- **Affected users:** anyone who used *Merge Project* to combine
  `.dasmix` files created with v0.7.1+ source projects. Proteins and
  identifications imported via earlier versions will still have NULLs in
  the previously-dropped columns — those values were never copied and
  cannot be retroactively recovered from the merge target. Re-importing
  from the original source project (now that the columns are copied
  correctly) is the only way to populate them.
