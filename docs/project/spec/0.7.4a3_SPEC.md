## Обзор

Два независимых направления оптимизации:

1. **Ion matching** — замена статической нарезки sub-batches на динамическую очередь чанков с промежуточными записями в БД.
2. **Protein map / de novo correction** — распараллеливание per-row цикла сравнения спектров с унификацией архитектуры генератора и прогресса.

Оба изменения не влияют на результат вычислений, только на производительность и поведение WAL-файла.

## Часть 1: Очередь чанков для ion matching

### 1.1 Текущая проблема

`ion_actions.py` делит `batch_size` на ровно `worker_count` sub-batches и запускает их через `asyncio.gather`. Все воркеры стартуют одновременно, и следующий DB-batch не читается, пока последний из sub-batches не завершится. Если один sub-batch содержит «тяжёлые» идентификации (длинные последовательности, много PTM-вариантов), остальные ядра простаивают.

### 1.2 Целевая архитектура

Заменить статическую нарезку на **`ProcessPoolExecutor` + `asyncio` task queue** с чанками фиксированного размера. Воркер-процессы берут следующий чанк сразу после завершения предыдущего (work stealing).

#### Параметры

| Параметр | Формула | Пример (cpu=8, batch=5000) |
|---|---|---|
| `chunk_size` | `int(batch_size / worker_count)` | 625 |
| `worker_count` | `max_cpu_threads or cpu_count - 1` | 7 |
| `flush_every` | `worker_count` завершённых чанков | 7 (≈4375 обработано) |

`batch_size` из `config.identification_processing_batch_size` теперь ограничивает **максимальный объём данных одновременно в памяти** (все чанки в полёте), а не «объём одной итерации».

#### Схема работы

```
DB READ  ──► chunk_queue (maxsize=worker_count)
                │
       ┌────────┴───────────────────────────────┐
       │  asyncio task queue (одна coroutine)   │
       │  while chunk_queue not empty:           │
       │    future = executor.submit(chunk)      │
       │    await future                         │
       │    results.append(future.result())      │
       │    completed += 1                       │
       │    if completed % flush_every == 0:     │
       │      await _flush_to_db(results)        │
       │      results.clear()                    │
       └────────────────────────────────────────┘
                          │
                   DB WRITE + _commit()
```

**Ключевые свойства:**
- `ProcessPoolExecutor` живёт на всю операцию (не пересоздаётся на каждый batch).
- Число одновременно «в полёте» задач = `worker_count` (семафор или `asyncio.as_completed`).
- DB-запись происходит каждые `flush_every` завершённых чанков — не реже чем ~раз в `batch_size` идентификаций.
- WAL не раздувается, т.к. flush не ждёт конца всего offset-цикла.

### 1.3 Изменяемые файлы

#### `dasmixer-gui/src/dasmixer/gui/actions/ion_actions.py`

Текущая функция `_compute_batch` и весь цикл с `get_identifications_with_spectra_batch` заменяются на новую логику очереди.

**Ключевые изменения:**
- Удалить нарезку `sub_batches = [worker_batch[i:i+chunk_size] ...]`.
- Убрать `asyncio.gather(*futures)` как единственный паттерн сбора.
- Реализовать `asyncio.Semaphore(worker_count)` или `asyncio.as_completed` для ограничения одновременно летящих задач.
- Добавить счётчик завершённых чанков и вызов `_flush_to_db` при `count % flush_every == 0`.
- Прогресс обновлять по числу обработанных идентификаций (накопительно), а не по batch-итерации.

**Псевдокод новой логики:**

```python
sem = asyncio.Semaphore(worker_count)
pending: list[asyncio.Future] = []
accumulated_results: list[dict] = []
completed_chunks = 0

async def submit_chunk(chunk):
    async with sem:
        return await loop.run_in_executor(executor, process_identifications_batch, chunk, ...)

# читаем все чанки из текущего DB-offset и кладём в очередь задач
chunks = [worker_dicts[i:i+chunk_size] for i in range(0, len(worker_dicts), chunk_size)]
tasks = [asyncio.create_task(submit_chunk(chunk)) for chunk in chunks]

for coro in asyncio.as_completed(tasks):
    result = await coro
    accumulated_results.extend(result)
    completed_chunks += 1
    if completed_chunks % flush_every == 0:
        await _flush_to_db(accumulated_results)
        accumulated_results.clear()

# финальный flush остатка
if accumulated_results:
    await _flush_to_db(accumulated_results)
```

#### `dasmixer-cli/src/dasmixer/cli/commands/calculate.py`

Сейчас `process_identifications_batch` вызывается синхронно без параллелизма. Применить аналогичную очередную логику через `concurrent.futures.ProcessPoolExecutor` + `as_completed` (sync-версия).

**Задачи:**
- Выделить общую утилитарную функцию `run_identification_queue(worker_dicts, executor, params, flush_callback, progress_callback)` в новый модуль `dasmixer.api.calculations.spectra.queue_runner` (core, без GUI-зависимостей).
- GUI (`ion_actions.py`) и CLI (`calculate.py`) используют эту общую функцию, передавая свои `flush_callback` и `progress_callback`.

### 1.4 Новый модуль `queue_runner.py`

**Путь:** `dasmixer-core/src/dasmixer/api/calculations/spectra/queue_runner.py`

```python
async def run_identification_queue(
    worker_dicts: list[dict],
    executor: ProcessPoolExecutor,
    chunk_size: int,
    flush_every: int,
    process_fn: Callable,            # process_identifications_batch
    process_fn_kwargs: dict,
    flush_callback: Callable[[list[dict]], Awaitable[None]],
    progress_callback: Callable[[int], None] | None = None,
    stop_check: Callable[[], bool] | None = None,
) -> int:
    """Возвращает число обработанных идентификаций."""
```

Правила:
- Использует именованный логгер `dasmixer.api.calculations.spectra.queue_runner`.
- Не импортирует ничего из `dasmixer.gui.*`.
- `stop_check` — опциональный кооперативный флаг остановки.

## Часть 2: Многопоточность protein map / de novo correction

### 2.1 Текущая проблема

`map_proteins` — async-генератор. Внутри цикла по строкам BLAST-результатов:
- `SeqFixer.get_matched_ppm(...)` — CPU-bound, перебор PTM-комбинаций.
- `_pick_best_override(...)` → множественные вызовы `match_predictions(...)` — CPU-bound.

Всё это выполняется последовательно в главном async-цикле. На проекте с тысячами de-novo идентификаций это доминирует по времени.

### 2.2 Целевая архитектура

#### Рефакторинг `map_proteins`

Убрать async-генератор. Заменить на обычную async-функцию с **хуком прогресса**:

```python
async def map_proteins(
    project: Project,
    tool_settings: dict[int, dict],
    ion_params: dict,
    fragment_charges: list[int],
    seqfixer_params: dict,
    batch_size: int = 5000,
    sample_id: int | None = None,
    use_src_protein_ids: bool = False,
    progress_callback: Callable[[int, int], None] | None = None,
    stop_check: Callable[[], bool] | None = None,
) -> None:
```

- `progress_callback(processed: int, total: int)` — вызывается после каждого batch.
- `stop_check()` — кооперативная остановка, проверяется после каждого batch.
- Запись результатов (`project.add_peptide_matches_batch`) выполняется **внутри** `map_proteins`.

**Важно:** изменение сигнатуры требует обновления всех вызывающих сторон (GUI `protein_map_action.py`, CLI `calculate.py`, пример в `docs/api/pipeline.md`).

#### Распараллеливание per-row цикла

Выделить воркер-функцию верхнего уровня (picklable):

```python
def process_protein_map_row(
    row_dict: dict,           # сериализованная строка BLAST-результата
    mz_array: list[float],
    intensity_array: list[float],
    pepmass: float,
    charge: int,
    seqfixer: SeqFixer,       # пиклуется — проверено
    ion_match_params_dict: dict,
    fragment_charges: list[int],
) -> dict:                    # результирующая строка для matches_df
```

Путь: `dasmixer-core/src/dasmixer/api/calculations/peptides/protein_map_worker.py`

**Особенности:**
- `IonMatchParameters` создаётся внутри воркера из `ion_match_params_dict` (копия на каждый вызов — устраняет гонку `params.charges`/`params.ions`).
- `SeqFixer` передаётся как аргумент (один объект на tool, пиклуется).
- Воркер не обращается к БД и не импортирует `dasmixer.gui.*`.

#### Интеграция очереди в `map_proteins`

По аналогии с Частью 1 — `ProcessPoolExecutor` + `asyncio.as_completed` внутри цикла по batch:

```python
# внутри map_proteins, после получения blast_df и spectra_map:
partial_rows = [row for row in blast_df.itertuples() if row.identity < 1.0]
chunks = chunked(partial_rows, chunk_size)

async for chunk_result in run_protein_map_queue(chunk, executor, seqfixer, ...):
    # merge chunk_result обратно в blast_df
    ...

# identity == 1.0 строки обрабатываются как сейчас (без воркера)
await project.add_peptide_matches_batch(matches_df)
```
