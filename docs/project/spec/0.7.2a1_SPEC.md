## 0. Краткое содержание

Релиз вводит показатель **LCRR (Longest Consecutive Run Ratio)** в пайплайн Ion Match, по аналогии с уже реализованным в `0.7.1a1` показателем **Quality**: расчёт **уже есть** (поле `MatchResult.longest_consec_run_rate`, функция `calculate_longest_consec_run_ratio` в `quality_calculations.py`) → нужно провести значение через схему БД → сохранение при расчёте Ion Coverage → фильтр `Min LCRR` в Preferred settings инструмента → учёт в Select Preferred → отображение колонкой `LCRR` в таблице Peptides.

LCRR — косвенный показатель качества спектра: отношение длины максимальной непрерывной последовательности совпавших ионов одного типа к длине пептида. Диапазон значений: `[0, 1]`.

> Работы по расчёту LCRR не требуется — задача полностью "проводочная": по аналогии с полями `quality`/`intensity_coverage`, добавить колонку в БД, прокинуть значение через `identification_processor.py` → `put_identification_data_batch` → SQL SELECT'ы → GUI (форма настроек + таблица).

## 1. Решения по уточняющим вопросам (согласованы с разработчиком)

| # | Вопрос | Решение |
|---|---|---|
| 1 | NULL-обработка LCRR в фильтре Select Preferred (normal-пул) | Строгая логика, симметрично `quality`: `AND i.lcrr IS NOT NULL AND i.lcrr >= ?`. Идентификации без вычисленного LCRR не могут стать preferred (через normal-пул). |
| 2 | Область действия `min_lcrr` | Фильтр применяется только к **normal**-пулу (`get_idents_for_preferred`, `ignore_criteria=False`). Для **trusted**-пула (`ignore_criteria=True`, `get_all_idents_for_preferred`) фильтр LCRR, как и все остальные пороги, не применяется. |
| 3 | Legacy-функция `select_preferred_identifications` (pandas-подход, `matching.py`) | **Не трогаем.** Она не используется в актуальном пайплайне (ни GUI, ни актуальный CLI-путь `full-pipeline` её не вызывают; используется только в устаревшей CLI-команде `select-preferred`, вне скоупа задачи). LCRR туда не добавляется. |
| 4 | Значение LCRR при ошибке расчёта в `process_single_ident`/error-handler | По аналогии с `quality`: **`None`** (а не `0`, как для `intensity_coverage`, где 0 нужен специально для защиты от бесконечного повторного пересчёта через `only_missing`-фильтр по `intensity_coverage IS NULL`). Повторный пересчёт всё равно исключается через `intensity_coverage`. |

## 2. Текущее состояние (контекст для исполнителя)

### 2.1 Расчёт LCRR — уже реализован, трогать не нужно
- `dasmixer-core/src/dasmixer/api/calculations/spectra/quality_calculations.py`, функция `calculate_longest_consec_run_ratio(matches, sequence) -> float` (строки 33–56) — уже вычисляет LCRR.
- `dasmixer-core/src/dasmixer/api/calculations/spectra/ion_match.py`:
  - `MatchResult` (dataclass, строки 70–91) уже содержит поле `longest_consec_run_rate: float` (последнее поле).
  - `match_predictions()` (строки 93–…) уже вызывает расчёт и заполняет `MatchResult.longest_consec_run_rate` (включая fallback `0.0` в ветке `total_peaks == 0`, строка ~145).
- **Задачи по расчёту НЕТ.** Работа только по проводке уже готового значения.

### 2.2 Схема БД (`schema.py`)
- Таблица `identification` (строки 100–126) содержит аналогичные по смыслу поля: `intensity_coverage REAL`, `quality REAL` (последняя добавлена в 0.7.1). Поля `lcrr` нет.

### 2.3 Миграции (`migrations.py`)
- `MIGRATIONS` содержит записи для `0.2.0`, `0.3.0`, `0.7.0`, `0.7.1` (последняя — образец: `ALTER TABLE identification ADD COLUMN quality REAL;` + 2 другие колонки).
- Механизм `apply_migrations()` уже рабочий, вызывается из GUI при открытии проекта.

### 2.4 Версии (`versions.py`)
- `APP_VERSION = "0.7.1a4.dev1"`, `PROJECT_VERSION = "0.7.1"`.
- `_version_lt`/`_version_gt` в `migrations.py` парсят версию как `tuple(int(x) for x in a.split('.'))` — **суффиксы (`a1`, `.dev1`) в `PROJECT_VERSION` недопустимы**, должна быть чисто числовая точечная версия.

### 2.5 Расчёт Ion Coverage / batch worker
- `dasmixer-core/src/dasmixer/api/calculations/spectra/identification_processor.py`:
  - `process_single_ident()` — 3 ветки возврата результата (trust-PPM branch ~строка 160, основная ветка ~строка 270), каждая уже вызывает `match_predictions()` и возвращает dict с полями `intensity_coverage`, `ions_matched`, `ion_match_type`, `top_peaks_covered`, `quality`, и др. — во всех return-точках нужно добавить `"longest_consec_run_rate": match_result.longest_consec_run_rate`.
  - Ветка обработки ошибки в `process_identificatons_batch()` (~строка 394–409) собирает fallback-словарь с `"quality": None` — по аналогии добавить `"longest_consec_run_rate": None`.
- `dasmixer-core/src/dasmixer/api/project/mixins/identification_mixin.py::put_identification_data_batch()` (строки 504–557) — batch UPDATE по списку dict; сейчас пишет `quality` (среди прочих). Нужно аналогично добавить запись `lcrr`.
- `clear_calculations()` (строки 559–590) — глобальный сброс расчётных полей (`intensity_coverage`, `quality`, и т.д. → `NULL`). Нужно добавить `lcrr = NULL`.

### 2.6 Preferred selection (актуальный пайплайн)
- `dasmixer-core/src/dasmixer/api/calculations/peptides/matching.py::calculate_preferred_identifications_for_file()` (строки 98–234) — актуальная функция, вызывается из GUI (`ion_actions.py`, `matching_section.py`) через `tool_settings_section.get_tool_settings_for_matching()`.
  - Для normal-пула (не `ignore_criteria`) читает `min_quality = tool_params.get("min_quality", 0.25)` и передаёт в `project.get_idents_for_preferred(..., min_quality=min_quality)`.
  - По аналогии нужно добавить чтение `min_lcrr = tool_params.get("min_lcrr", 0.2)` и передачу в `get_idents_for_preferred(..., min_lcrr=min_lcrr)`.
  - Для trusted-пула (`ignore_criteria=True`) вызывается `get_all_idents_for_preferred()` без порогов — LCRR туда не подмешивается (см. решение п.2).
- `identification_mixin.py::get_idents_for_preferred()` (строки 210–288) — SQL с явными фильтрами (score, ppm, coverage, length, peaks, ions, top_peaks) + опциональный `min_quality` (строки 283–285: `AND i.quality IS NOT NULL AND i.quality >= ?`, добавляется только если `min_quality is not None`). LCRR добавляется по тому же паттерну.
- `identification_mixin.py::get_all_idents_for_preferred()` (строки 290–329) — без фильтров, но SELECT нужно расширить полем `i.lcrr`, т.к. это тот же shape DataFrame, что и у `get_idents_for_preferred` (конкатенируются вместе в `matching.py`). Значение не используется для фильтрации, но колонка должна присутствовать для консистентности схемы результирующего DataFrame (хотя на практике `pd.concat` допускает разные наборы колонок — тем не менее для консистентности с остальными полями (`ppm`, `intensity_coverage`) добавляем).

### 2.7 Legacy CLI-путь (не трогаем)

## 4. Интеграционная проверка (после реализации всех слоёв)

1. **Миграция:** открыть существующий проект версии `0.7.1` в GUI → диалог обновления схемы → `project_metadata.version` становится `0.7.2`; колонка `lcrr` присутствует в таблице `identification` (проверить через SQLite console / gear-диалог столбцов таблицы Peptides — появляется `LCRR` в списке доступных колонок).
2. **Расчёт Ion Coverage:** запустить расчёт (`Calculate Ion Coverage` action) на наборе идентификаций → после завершения колонка `LCRR` в таблице Peptides заполнена числовыми значениями `0.0–1.0` для обсчитанных строк.
3. **Preferred settings — сохранение:** открыть карточку инструмента на вкладке Peptides → изменить `Min LCRR` (например, на `0.5`) → нажать `Save settings` → перезагрузить вкладку/проект → значение `0.5` сохранилось.
4. **Preferred settings — валидация:** ввести в `Min LCRR` значение `1.5` → `Save settings` → ожидается ошибка `"Min LCRR must be in [0, 1]"`, сохранение не происходит.
5. **Select Preferred с фильтром LCRR:** выставить `Min LCRR` заведомо высоким (например, `0.99`) для инструмента без `Trust all identifications` → запустить `Select Preferred` → идентификации этого инструмента с `lcrr < 0.99` или `lcrr IS NULL` не выбираются preferred (а если нет альтернативного trusted-кандидата — спектр остаётся без preferred).
6. **Trust all identifications:** для инструмента с включённым `Trust all identifications` — `Min LCRR` не влияет на выбор preferred (весь trusted-пул участвует независимо от LCRR).
7. **Таблица Peptides:** колонка `LCRR` видна по умолчанию среди столбцов таблицы; для идентификаций без расчёта — пустое значение; сортировка/скрытие колонки работает как для прочих числовых колонок.
8. **Clear Calculations:** выполнить `Clear Calculations` action → все значения `identification.lcrr` становятся `NULL` (проверить в таблице — колонка `LCRR` пуста для всех строк).
