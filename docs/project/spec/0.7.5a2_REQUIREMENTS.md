## Улучшение логики работы peptide_match и I/L combinatorics

Общая концепция:
- Оптимизация: вместо chunked-поиска делаем полные выгрузки белковой БД в формат .fasta на диск; выгружаем уникальные канонически последовательности так же.
- При выгрузке с флагом I/L Combinatorics выгружаем все последовательности с заменой I->L (и белки, и пептиды)
- Для de novo correction/save AA substitution: делаем поиск двуэтапный. На первом этапе только точные совпадения, при втором проходе выполняем поиск со сниженной до заданного порога точностью
- заполняем новые поля при поиске

### Выгрузка белков во временные файлы

npysearch работает с текстовыми файлами, даже при вызове самой библиотеки происходит создание временных .fasta-файлов. Поэтому первым этапом предлагается создание двух файлов выгрузки белковой билиотеки:

выгружаем во временную папку: {tmp_dir}/peptide_match/project_name_stem/{datetime}. эта папка создаётся в заданной в настройках временной папке для обычных (не large) файлов.

В неё выгружаются два файла:

- proteins.fasta - выгрузка белковой библиотеки
- proteins_lic.fasta - та же библиотека с полной заменой I->L в последовательностях (только если хотяя бы для одного инструмента есть флаг I/L Combinatorics)

Библиотеку последовательностей при этом (в формате dict {protein_id: protein sequence} оригинальную из памяти не выгружаем, она ещё понадобится.

### Поиск уникальных последоватлеьностей и создание временных файлов

На первом этапе мы делаем чтение уникальных канонических последовательностей из БД для инструмента:

```sql
select * from 
             (select canonical_sequence, count(*) as cnt, group_concat(id) as idlist, min(abs(ppm)) as min_ppm, length(canonical_sequence) as seq_length
                from identification where tool_id=1 GROUP by canonical_sequence) where seq_length > ? order by canonical_sequence
```

Делаем ряд важных изменений:
- Уходим от логики denovo_correction_ppm, поиск осуществляем независимо от PPM последовательности
- Пропускаем пептиды длиной менее max(min_lenght, 4) аминокислот, где min_length - параметр инструмента. Этот фильтр делаем в запросе.
- пропускаем пептиды, состоящие только из одной аминокислоты подряд (напр. GGGGGGGG)
- преобразуем I->L по всем последоватлеьностям (если стоит флаг I/L combinatorics)

Для получения списка последоватлеьностей делаем новый метод в Project, а именно в peptide_mixin. фильтрацию и преобразование делаем в рамках этого же метода.

список последовательностей также сохраняем в fasta_file в формате st1_plain_{tool_id}.fasta.

записи в файле формируем в виде:
```
>{index}
{canonical_sequence}
```

### Stage1: первичный поиск

Выполняем поиск с npysearch.blast() с условием identity=1.0

Для запуска npysearch меняем рабочую директорию на временную, куда сохранены файлы .fasta, потом возвращаем как было.

Найденные на этом этапе последовательности - точные совпадения. Процессинг для них:

idlist (QueryId в результатах npy.blast) разделяем через split по запятой (функционал проверен, npysearch позволяет использвоать длинные queryId)

Если использован режим I/L combinatorics - получаем из сохранённого выше словаря последовательностей по protein_id и номеру начальной аминокислоты. Если найденная по белку и старотовй позиции последоватлеьность не равна найденной - запоминаем, что выполнена коректировка

Запись результатов этого этапа в БД делаем через пул до protein_mapping_batch_size идентификаций, при накоплении или при завершении - записываем в БД через executemany и последующий checkout (project.save(checkpoint=True))

также если есть флаг de novo correction или AA substitution - храним в памяти как set все QueryId, для которых получены результаты.

Записываем в таблицу peptide_match минимум информации:
- matched_sequence
- protein_id
- identification_id
- identity
- substitution (=0)
- fasta_start (из поля TargetMatchStart в ответе npysearch)
- correction (=lic если была корректировка)

### Stage 2: Перебор со сниженной точностью

Для этого этапа есть сложное условие: `(Установлен флаг De Novo correction ИЛИ флаг Save AA substitution) И (в параметрах инструмента protein_identity < 1.0)`.

Выполняем для оставшихся последовательностей поиск с identity, заданным в параметрах. Результаты обрабатываем в рамках шага 3

### Stage 3: Объединение со спектральными данными

Условие: флаг De Novo correction или флаг save AA substitutions

Проверяем фрагментацию ионов для результатов шага 2, аналогично текущей логике для результатов со сниженным identity.

Для всех результатов поиска в этой секции реализуем текущую логику:
- Оставляем только варианты последовательности с наибольшим найденным identity
- Определяем PPM и возможные PTM с помощью SEQFixer
- определяем физические критерии с помощью protein_map_worker

Нюансы:
- Для peptide_match также сохраняем новые параметры: quality, lcrr, unconfirmed_ptms
- Меняем параметры корректировки match'а: PPM, LCRR, Quality, Intensity Coverage. если по хотя бы одному из выбранных критериев есть улучшение (снижение abs ppm, повышение остальных) - сохраняем как скорректированную, записываем текущий набор полей, сохраняем в БД с correction=denovo
- Сохранение AA Substitution делаем как сейчас, без изменений
- При включенном i/l combinatorics - тот же механизм сохранение

## Изменения GUI

### Tool settings

На вкладке peptides, секция tool settings: меняем набор match correction criteria на `PPM, LCRR, Quality, Intensity Coverage`.

Меняем отображение прогресса при protein match:

progress bar запускаем так:
- Create sequence databases...
- Simple search (identity=1.0)...
- Saving simple search results ({uq_sequences_no} unique sequences)...
- Correction search (identity={identity})...
- Processing corrected sequences ({processed} of {total})...

при identity = 1.0 первые три этапа двигают progress bar по 33%, два последних не отображаются

При меньшем значении:
- первые четыре этапа заполняют шкалу в сумме до 60% (по 15% на этап). Прогресс последнего шага увеличивается по мере расчёта, аналогично ion_coverage, но рассчитывается в интервале от 60 до 100%, сохранение данных проходит в процессе

## Доработки в логике preferred selection:

Модифицируем запрос, все фильтры, следующие из обновлённой схемы, реализуем по следующей логике:
- (i.ppm < ? OR (m.correction='denovo' AND m.matched_ppm < ?) # примерно аналогично для остальных с поправками на min/max
- убираем из calculate_preferred_identifications_for_file логику выбора между ppm и denovo_ppm
- проверяем, что дальнейшая логика консистентна
