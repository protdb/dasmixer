## 1. Цель и ограничения

### Цель

Добавить два независимых блока функциональности:

1. **Портативные проекты** — корректное сохранение SQLite WAL, операция VACUUM, новые пункты меню и CLI-команды.
2. **Импорт проекта** — слияние данных одного `.dasmix`-файла в другой с сохранением внутренних зависимостей и разрешением конфликтов ID/имён.

### Ограничения

- Все новые публичные методы Project — **async**.
- Импорт реализован как `ImportProjectMixin`; в MRO добавляется к существующей цепочке.
- GUI строго соблюдает Flet 0.80.5 API (FilePicker через `await ft.FilePicker().pick_files(...)`).
- Никакого `__init__.py` в `src/dasmixer/` поддиректориях (namespace packages).
- Таблицы `sample_status_cache` и `report_parameters` при импорте **не** переносятся.

## 2. Блок A — Портативные проекты

### 2.1 Core: `ProjectLifecycle`

**Файл:** `dasmixer-core/src/dasmixer/api/project/core/lifecycle.py`

#### Задача A-1: `save(checkpoint=False)`

Добавить необязательный аргумент `checkpoint: bool = False` к методу `save()`.

```python
async def save(self, checkpoint: bool = False) -> None:
```

Логика:
1. Обновить `modified_at` в `project_metadata` (существующая логика).
2. Выполнить `await self._db.commit()`.
3. Если `checkpoint is True` — выполнить дополнительно:
   ```sql
   PRAGMA wal_checkpoint(TRUNCATE);
   ```
   Это сбрасывает WAL-файл в основной файл БД и обнуляет WAL, что обеспечивает корректное портативное копирование файла без необходимости переносить `-wal`/`-shm` сателлиты.

#### Задача A-2: `save_as()` — использовать checkpoint

В методе `save_as()` заменить вызов `await self.save()` на `await self.save(checkpoint=True)`.

Это гарантирует, что `shutil.copy2` копирует уже полностью сброшенный файл.

#### Задача A-3: `vacuum()`

Добавить новый метод:

```python
async def vacuum(self) -> None:
    """Rebuild the database file, compacting free pages (SQLite VACUUM)."""
    if not self._db:
        raise RuntimeError("Project not initialized")
    await self._db.execute("VACUUM")
    logger.info("Project vacuumed")
```

> **Примечание:** SQLite требует, чтобы VACUUM выполнялся вне транзакции. `aiosqlite` в режиме autocommit (isolation_level=None) это поддерживает; если соединение в WAL-режиме с незакоммиченной транзакцией — перед VACUUM следует вызвать `save()`.

Безопасный порядок в вызывающем коде: `await project.save(checkpoint=True)` → `await project.vacuum()`.

## 3. Блок B — Импорт проекта

### 3.1 Core: `ImportProjectMixin`

**Файл:** `dasmixer-core/src/dasmixer/api/project/mixins/import_project_mixin.py` (новый)

---

#### Сигнатура

```python
from typing import Literal, Callable

async def import_project(
    self,
    source_path: str | Path,
    tool_match: Literal['name', 'parser'] | None = 'parser',
    subset_match: bool = True,
    project_settings_match: bool = False,
    sample_match: bool = True,
    conflict_suffix: str = "_1",
    status_callback: Callable[[str, float], None] | None = None,
) -> None:
```

**Параметры:**

| Параметр | Тип | По умолч. | Описание |
|---|---|---|---|
| `source_path` | `str\|Path` | — | Путь к импортируемому `.dasmix`-файлу |
| `tool_match` | `'name'\|'parser'\|None` | `'parser'` | Стратегия объединения инструментов |
| `subset_match` | `bool` | `True` | Объединять субсеты по имени |
| `project_settings_match` | `bool` | `False` | Перезаписывать настройки проекта |
| `sample_match` | `bool` | `True` | Пытаться объединить одноимённые сэмплы |
| `conflict_suffix` | `str` | `"_1"` | Суффикс при конфликте имён |
| `status_callback` | `Callable[[str, float], None]\|None` | `None` | Прогресс-колбэк: (название_таблицы, доля) |

---

#### Детальная логика

##### Шаг 0. Предварительная настройка

Открыть соединение с `source_path` (только чтение: `PRAGMA query_only = ON`):

```python
src_db = await aiosqlite.connect(str(source_path))
src_db.row_factory = aiosqlite.Row
await src_db.execute("PRAGMA query_only = ON")
```

Установить на **целевом** соединении (self._db) для ускорения:
```sql
PRAGMA synchronous = NORMAL;
PRAGMA cache_size = -65536;
```

После окончания импорта (в `finally`) — вернуть обратно:
```sql
PRAGMA synchronous = FULL;
PRAGMA cache_size = -2000;
```

Всю операцию вести **в одной транзакции** на целевом соединении (`BEGIN` в начале, `COMMIT` в конце; при ошибке — `ROLLBACK`).

> **Обоснование не использовать ATTACH DATABASE для основного потока данных:**  
> Таблицы `tool`, `subset` и `sample` небольшие и требуют логики маппинга ID, которую удобнее реализовать в Python. Остальные таблицы (spectre, identification, peptide_match и т.д.) крупные — для них используем `ATTACH DATABASE` и `INSERT INTO ... SELECT ... FROM src.table` с арифметическим смещением ID прямо в SQL.

##### Шаг 1. Маппинг `subset`

Получить все субсеты из `src_db`.

**Если `subset_match=True`:**  
Для каждого субсета из source: найти в целевом БД по имени.
- Найден → записать маппинг `src_id → target_id`.
- Не найден → вставить новый `INSERT INTO subset (name, details, display_color)`, записать маппинг.

**Если `subset_match=False`:**  
Для каждого субсета: если имя уже есть в целевом → добавить `conflict_suffix` к имени (итеративно, пока не уникально). Вставить, записать маппинг.

Результат: `dict[int, int]` — `subset_id_map: {src_id → target_id}`.

##### Шаг 2. Маппинг `tool`

Получить все инструменты из `src_db`.

**Если `tool_match='parser'`:**  
Для каждого инструмента source: найти в целевом по полю `parser`.
- Найден (первый совпадающий) → маппинг `src_id → target_id`.
- Не найден → вставить как новый.

**Если `tool_match='name'`:**  
Аналогично, но поиск по полю `name`.

**Если `tool_match=None`:**  
Все инструменты source добавляются как новые. Если имя конфликтует с существующим (при `INSERT` поднимается UNIQUE-ошибка) → добавить `conflict_suffix` к имени итеративно.

Результат: `dict[int, int]` — `tool_id_map: {src_id → target_id}`.

##### Шаг 3. Маппинг `sample`

Получить все сэмплы из `src_db`.

Получить максимальный `id` в целевой таблице `sample`: `base_sample_id = MAX(id)` (0 если пусто).

**Если `sample_match=True`:**  
Для каждого сэмпла source: найти в целевом по полю `name`.
- Найден → маппинг `src_id → target_id` (не вставляем).
- Не найден → `new_id = src_id + base_sample_id`, вставить с явным ID и скорректированным `subset_id` через `subset_id_map`.

**Если `sample_match=False`:**  
Если имя конфликтует → добавить `conflict_suffix` итеративно.  
`new_id = src_id + base_sample_id`, вставить с этим ID.

Результат: `dict[int, int]` — `sample_id_map: {src_id → target_id}`.

##### Шаг 4. Вставка крупных таблиц через ATTACH + SQL

Для всех оставшихся таблиц используем `ATTACH DATABASE` на целевом соединении:

```sql
ATTACH DATABASE '<source_path>' AS src;
```

Получаем базовые смещения ID для каждой таблицы:

```python
base_ids = {}
for table in ['spectre_file', 'spectre', 'identification_file',
              'identification', 'peptide_match',
              'protein_identification_result', 'protein_quantification_result',
              'generated_reports', 'saved_plots']:
    row = await self._fetchone(f"SELECT COALESCE(MAX(id), 0) AS max_id FROM {table}")
    base_ids[table] = row['max_id']
```

###### 4.1 `protein`

Таблица `protein` использует текстовый PK (`id TEXT PRIMARY KEY`) — конфликтов числовых ID нет.

```sql
INSERT OR IGNORE INTO protein
SELECT * FROM src.protein;
```

###### 4.2 `spectre_file`

```sql
INSERT INTO spectre_file (id, sample_id, format, path)
SELECT
    sf.id + :base_sf,
    :sample_id_map[sf.sample_id],   -- не SQL, логика через CASE WHEN или temp table
    sf.format,
    sf.path
FROM src.spectre_file sf;
```

Поскольку `sample_id_map` — произвольный маппинг (не смещение), создаём временную таблицу маппинга:

```sql
CREATE TEMP TABLE _sample_id_map (src_id INTEGER PRIMARY KEY, tgt_id INTEGER);
-- вставляем все пары из sample_id_map
INSERT INTO _sample_id_map VALUES (?, ?), ...;
```

Затем:

```sql
INSERT INTO spectre_file (id, sample_id, format, path)
SELECT
    sf.id + :base_sf,
    m.tgt_id,
    sf.format,
    sf.path
FROM src.spectre_file sf
JOIN _sample_id_map m ON m.src_id = sf.sample_id;
```

- При любом исключении — `await self._db.execute("ROLLBACK")` + `await src_db.close()` + reraise.
- Возвращать `PRAGMA synchronous` и `cache_size` в `finally`.

#### Задача B-4: Обработчик `merge_project()` в `app.py`

```python
async def merge_project(self, e=None) -> None:
```

Логика:
1. `files = await ft.FilePicker().pick_files(...)` — выбрать `.dasmix`-файл.
2. Если файл не выбран — выйти.
3. Показать `MergeOptionsDialog`. Получить `result = await dialog.show()`.
4. Если `result is None` — выйти (Cancel).
5. Показать `ProgressDialog("Merging project...")`.
6. Передать колбэк:
   ```python
   def on_progress(table: str, fraction: float):
       dialog.update_progress(fraction, f"Importing {table}...")
   ```
7. `await self.current_project.import_project(source_path=path, status_callback=on_progress, **result)`
8. Закрыть `ProgressDialog`.
9. `show_snack(self.page, "Project merged successfully", ft.Colors.GREEN_400)`
10. При ошибке — закрыть диалог, показать snack с ошибкой.

> **Примечание:** `status_callback` вызывается из `async` контекста; `ProgressDialog.update_progress` синхронный, это нормально в Flet (вызов из того же event loop).

## 5. Что НЕ входит в 0.6.0

- Пересчёт `sample_status_cache` после импорта — вручную через GUI.
- Импорт `report_parameters` — не переносится.

- Отмена (Cancel) в процессе импорта — `ProgressDialog` не cancelable.
