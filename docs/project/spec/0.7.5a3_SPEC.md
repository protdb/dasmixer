## 1. Находки исследования (контекст для исполнителя)

### 1.1 Где формируются подпись и hover

Единственные места в коде (дублирования в GUI нет):

- Подпись пика — `dasmixer-core/src/dasmixer/api/calculations/spectra/ion_match.py`, `get_matches_dataframe`, строка 297:
  ```python
  'label': f'{match.fragment.ion_type}{ion_pos}{loss_label}{charge_str}',
  ```
  Где `ion_pos = fragment.end - fragment.start` (стр. 280), `loss_label` — `''` / `-NH3` / `-H2O` / `±X.XX` (стр. 283–291), `charge_str = f'+{charge}'` только при заряде > 1 (стр. 277).
- Hover — `plot_matches.py`, `generate_spectrum_plot`, стр. 170–173:
  ```python
  customdata=np.stack((df['frag_seq'], df['label']), axis=-1),
  hovertemplate="%{customdata[1]} %{customdata[0]}<br>M/z: %{x}, Int.: %{y}<extra></extra>"
  ```
- Бар и аннотация — `plot_matches.py`, стр. 177–215: тело бара всегда `lightgray`, обводка — цвет типа иона (`get_ion_type_color`) либо `lightgray` для несовпавших; текст аннотации — цвет типа иона.

Все вьюеры используют один пайплайн: `get_spectrum_plot_data` → `make_full_spectrum_plot` → `match_predictions` + `get_matches_dataframe` → `generate_spectrum_plot`. Точки вызова: peptides tab (`peptide_ion_plot_view.py`), search section (`search_section.py`), CLI/экспорт (`export_workflow.py`), пример в `docs/api/ion_plot.md`.

### 1.2 Поведение `Fragmenter`/`Fragment` (проверено по peptacular)

- `Fragment.sequence` — **ProForma-строка с модификациями** (ре-сериализация через `annotation.serialize(include_plus=False)`); `unmod_sequence` — только буквы.
- `Fragment.start` инклюзивный, `Fragment.end` **эксклюзивный**: full-length фрагмент имеет `start == 0`, `end == len(residues)`.
- Потери (`-H2O`/`-NH3`) **не меняют** `fragment.sequence` — меняются только `loss`/`mass`/`mz`.
- `Fragmenter(sequence)` парсит строку один раз в `__init__`; `fragment()` вызывает `annotation.pop_labile_mods()` **на этом же объекте** (мутация). Поэтому после вызова `.fragment(...)` строка `fragmenter.annotation.serialize()` — это ровно та нормализованная последовательность без labile-модов, из которой строились фрагменты. Это и есть эталон для сравнения (D2).
- Для полного покрытия `slice(0, len)` сохраняет и N-term, и C-term, и внутренние модификации; full-length b и full-length y дают `sequence`, равную нормализованной последовательности пептида.

### 1.5 Проверено экспериментально (peptacular из venv проекта, 2026-11-26)

Скрипт: `Fragmenter(seq).fragment(['b','y'], [1], water_loss=True, ammonia_loss=True)`.

- `PEPTIDE`: full-length m/z `764.34612` (b-H2O), `782.35668` (b и y-H2O), `800.36724` (y); у всех `fragment.sequence == 'PEPTIDE'`.
- `PEP[+79.966]TIDE`: `fragmenter.annotation.serialize()` после `fragment()` → `PEP[79.966]TIDE` (знак `+` в моде отброшен). **Сравнение с сырой строкой из БД не сработало бы** — нормализация обязательна.
- `{+79.966}PEPTIDE` (labile): после `fragment()` аннотация сериализуется в `PEPTIDE`, все full-length фрагменты имеют `sequence == 'PEPTIDE'`. Сравнение по нормализованной строке работает.
- **b-full и y-full-H2O имеют одинаковый m/z** (`782.35668`): один экспериментальный пик может дать два precursor-матча (`P` и `P-H2O`). Это ожидаемая ситуация, а не экзотика (см. §5, п. 2).
- Прогон на синтетическом спектре подтвердил: Quality/LCRR/`ions_matched`/`top10` уменьшаются после исключения precursor-матчей; Intensity Coverage и `unconfirmed_ptms` не меняются; при «только прекурсор» — `0/0/0/0`, intensity > 0, `unconfirmed_ptms = 0`; `get_match_coverage([])` возвращает `{}` без исключений.

### 1.3 Где считаются метрики

Все шесть метрик считаются в `match_predictions` (`ion_match.py`, стр. 95–220) из одного списка `matches`:

| Метрика | Поле `MatchResult` | Как сейчас |
|---|---|---|
| Quality | `quality` | `calculate_peptide_quality(matches, ...)` |
| LCRR | `longest_consec_run_rate` | `calculate_longest_consec_run_ratio(matches, ...)` |
| Peaks covered | `max_ion_matches`, `top_matched_ion_type` | `get_match_coverage(matches)` |
| Top peaks covered | `top10_intensity_matches` | фильтр `matches` по интенсивности ≥ 10-го пика |
| Intensity Coverage | `intensity_percent` | `_get_matched_intensity_percentage(matches, intensity)*100` |
| Unconfirmed PTMs | `unconfirmed_ptms` | `calculate_unconfirmed_ptms(matches, sequence)` |

Потребители `match_predictions` (менять не нужно, изменения придут автоматически):
`identification_processor.process_single_ident` (запись в `identification`), `coverage_worker` (лайт-режим), `protein_map_worker` (запись в `peptide_match`), `plot_flow` (график).

Колонки БД (схема не меняется): `identification.quality/lcrr/ions_matched/ion_match_type/top_peaks_covered/intensity_coverage/unconfirmed_ptms`; аналогичные `peptide_match.quality/lcrr/matched_*`.

### 1.4 Потребители DataFrame разметки

`label`, `frag_seq`, `ion_pos` из `get_matches_dataframe` читаются **только** в `plot_matches.generate_spectrum_plot` (проверено по репозиторию). Поэтому добавление колонок безопасно; переименовывать существующие не нужно.

## 2. Функциональные требования

### 2.1 Определение пика прекурсора

Матч считается precursor-матчем, если:

1. он присутствует в `FragmentMatch`-списке, полученном `get_fragment_matches` (т.е. ион реально генерировался с текущими `IonMatchParameters` и попал в допуск);
2. `match.fragment.sequence == full_sequence`, где `full_sequence = fragmenter.annotation.serialize()` **после** вызова `fragment()` (нормализованная ProForma без labile-модов).

Следствия:

- full-length b и full-length y, а также их варианты с `-H2O`/`-NH3`, все попадают в прекурсор (потери не меняют `sequence`);
- на графике может быть несколько precursor-пиков — по одному на каждый вариант потерь/заряда;
- определение выполняется **на каждый матч**, а не на пик: если один экспериментальный пик совпал и с full-length, и с обычным ионом, обычный матч продолжает учитываться в метриках (D4, D9).

### 2.2 Отображение на графике

| Элемент | Обычный матч | Precursor-матч |
|---|---|---|
| Контур бара | цвет типа иона, width 2 | **чёрный**, width 2 |
| Тело бара | `lightgray` | `lightgray` (без изменений) |
| Текст аннотации | `label` (напр. `y8+2`) | `display_label` = `P` + loss + charge (напр. `P+2`, `P-H2O`) |
| Цвет текста аннотации | цвет типа иона | **чёрный** |
| Несовпавший пик | обводка `lightgray`, без аннотации | — |

Суффикс ` (Precursor peak)` в аннотацию **не** добавляется — только в hover.

### 2.3 Hover

- Обычный матч: `y8-H2O PEPTIDEE` + вторая строка `M/z: …, Int.: …` (как сейчас).
- Precursor-матч: `y8-H2O PEPTIDEE (Precursor peak)` + та же вторая строка.
- `label` в hover — **исходный** (тип иона + позиция + loss + charge), а не `P`-подпись.
- Несовпавшие пики — поведение не меняется.

### 2.4 Матрица метрик

| Метрика | Список матчей | Поведение |
|---|---|---|
| Quality (`quality`) | без precursor | прекурсор не учитывается |
| LCRR (`lcrr`) | без precursor | прекурсор не учитывается |
| Peaks covered (`ions_matched`, `ion_match_type`) | без precursor | прекурсор не учитывается |
| Top peaks covered (`top_peaks_covered`) | без precursor | прекурсор не учитывается |
| Intensity Coverage (`intensity_coverage`) | полный | прекурсор учитывается (код не меняется) |
| Unconfirmed PTMs (`unconfirmed_ptms`) | полный | прекурсор учитывается (код не меняется) |

Граничный случай (D11): если после исключения прекурсора список пуст —
`quality=0`, `lcrr=0`, `max_ion_matches=0`, `top_matched_ion_type=None`, `top10_intensity_matches=0`;
`unconfirmed_ptms` считается по полному списку, т.е. full-length матч подтверждает все PTM → `0`.
`total_peaks` и `intensity_percent` не меняются.

## 3. Изменения в core

### 3.1 `ion_match.py`

#### 3.1.1 Новый helper

```python
def is_precursor_match(match: FragmentMatch, full_sequence: str) -> bool:
    """True if the matched fragment covers the whole peptide sequence.

    ``full_sequence`` must be the normalised ProForma string produced by
    ``Fragmenter(sequence).annotation.serialize()`` *after* ``fragment()``
    (labile modifications already popped).
    """
    return match.fragment.sequence == full_sequence
```

#### 3.1.2 `MatchResult`

Добавить поле (в конец, с дефолтом — чтобы не ломать возможные внешние конструкторы):

```python
from dataclasses import dataclass, field
...
    unconfirmed_ptms: int
    precursor_matches: list[FragmentMatch] = field(default_factory=list)
```

`precursor_matches` — подмножество `fragment_matches` (те же объекты, не копии).

#### 3.1.3 `match_predictions`

- Заменить `frags = Fragmenter(sequence).fragment(...)` на сохранение объекта:
  ```python
  fragmenter = Fragmenter(sequence)
  frags = fragmenter.fragment(
      params.ions, params.charges,
      water_loss=params.water_loss,
      ammonia_loss=params.ammonia_loss,
  )
  full_sequence = fragmenter.annotation.serialize()
  ```
  Важно: `serialize()` вызывать **строго после** `fragment()` (labile-моды вырезаются внутри `fragment()`).
- После `get_fragment_matches` разложить матчи:
  ```python
  precursor_matches = []
  metric_matches = []
  for m in matches:
      if m.fragment.sequence == full_sequence:
          precursor_matches.append(m)
      else:
          metric_matches.append(m)
  ```
- Дальше:
  - `get_match_coverage(metric_matches)` (вместо `matches`);
  - `top10_intensity_matches` — по `metric_matches`;

- Ранний выход `total_peaks == 0`: без изменений (поле `precursor_matches` берётся из дефолта).

## 5. Граничные случаи

1. **Несколько матчей на одном пике.** Строки не дедуплицируются: на одном m/z может быть precursor- и обычная строка; бар и аннотация рисуются для каждой (наложение — существующее поведение). В метриках обычный матч учитывается, precursor — нет.
2. **Несколько precursor-пиков с разными потерями.** Каждый получает свою `P`-подпись (`P`, `P-H2O`, `P-NH3`, `P+2`, `P-H2O+2`, …). Дополнительно full-length b и y-H2O могут совпасть по m/z (проверено: `782.35668` для `PEPTIDE`) — тогда на одном пике будут две precursor-аннотации (`P` и `P-H2O`), обе чёрные.
3. **Пик на `pepmass`, не совпавший с full-length ионом.** Не выделяется и не подписывается (D3).
4. **Labile-модификации.** `Fragmenter` вырезает их до фрагментации; сравнение нормализованных строк это учитывает. Побочный эффект тот же, что у peptacular: такие модификации не видны в `fragment.sequence`.
5. **N/C-term модификации.** Для full-length b/y `slice(0, len)` сохраняет терминальные моды, поэтому равенство работает.
6. **`?`-модификации.** К моменту графика последовательности уже локализованы; если всё же придёт `?`, `Fragmenter` упадёт как и сейчас — поведение не меняем.
7. **Несовпавшие пики.** `is_precursor=False`, `display_label=None`, hover/вид без изменений.
8. **Заряд.** В `P`-подписи и hover используется заряд **совпавшего фрагмента** (`y8+2 → P+2`), а не заряд идентификации.

---

## 6. Ручной чек-лист проверки

1. Открыть спектр, где `y_n-H2O` совпадает с `pepmass`: есть precursor-пик с чёрным контуром и подписью `P` (или `P+2`), hover — `<исходный label> <frag_seq> (Precursor peak)`.
2. Убедиться, что обычные пики не изменились (цвет обводки, подпись, hover без суффикса).
3. Пересчитать ion coverage на спектре с precursor-пиком: Quality, LCRR, `ions_matched`, `top_peaks_covered` не увеличиваются/уменьшаются скачком из-за прекурсора; `intensity_coverage` и `unconfirmed_ptms` соответствуют старой логике.
4. Проверить случай, когда единственный матч — full-length: Quality=0, LCRR=0, `ions_matched`=0, `top_peaks_covered`=0, `unconfirmed_ptms`=0.
5. Проверить график в peptides tab и в search section — идентичная разметка.
6. Переоткрыть проект: метрики читаются из БД, миграция не запрашивается, `PROJECT_VERSION` остался `0.7.5`.
7. Проверить пептид с модификацией: `P`-подпись и hover содержат модифицированную последовательность в `frag_seq`.

## 7. Последствия и риски

- **Quality-гейт SeqFixer.** В `identification_processor` `allow_ptm = quality < quality_threshold`; после исключения прекурсора Quality может стать ниже, и перебор PTM будет запускаться чаще. Это ожидаемое следствие нового определения метрики; порог не меняем.
- **Preferred selection и Match correction criteria** (0.7.5a2) используют Quality/LCRR/Intensity Coverage; их решения могут измениться. Ожидаемо, отдельной логики не добавляем.
- **Старые проекты.** Метрики, посчитанные ранее, остаются «старыми» до повторного расчёта; автоматического пересчёта нет (D12). Сравнение проектов, посчитанных до/после обновления, некорректно — зафиксировать в changelog при его написании.
- **Наложение аннотаций** на одном пике — существующее поведение, не исправляем.
- **Peptacular labile-моды** вырезаются библиотекой; если в будущем понадобится учитывать их в `frag_seq`, это отдельная задача.
