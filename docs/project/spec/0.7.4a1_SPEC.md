## 0. Общие решения по итогам обсуждения

1. **Расширение скоупа.** Помимо 4 директорий, перечисленных в REQUIREMENTS
   (`dasmixer-core/.../api/reporting`, `dasmixer-gui/.../gui/reporting`,
   `dasmixer-gui/.../gui/reports`, `dasmixer-gui/.../gui/views/tabs/reports`),
   правки коснутся:
   - **новой** директории `dasmixer-core/src/dasmixer/reports/` (модули
     конкретных отчётов; см. §1);
   - `dasmixer-core/src/dasmixer/api/project/schema.py`,
     `migrations.py`, `mixins/report_mixin.py`,
     `mixins/import_project_mixin.py` — колонка `name` в `generated_reports`,
     миграция схемы, синхронизация импорта проектов (правило #15 AGENTS.md);
   - `dasmixer-core/src/dasmixer/versions.py` — `PROJECT_VERSION = "0.7.4"`
     (по прямому указанию в REQUIREMENTS, разрешение от Developer получено);
   - `dasmixer-gui/src/dasmixer/gui/main.py` — строка
     `import dasmixer.gui.reports.forms` заменяется на новый механизм
     авто-обнаружения форм (см. §2.5).
   Никакие другие пакеты/модули не трогаем.

2. **Исключение из правила #11 AGENTS.md.** Правило "Core reports must not
   import from `dasmixer.gui.*`" смягчается: файлы `form.py` внутри
   `dasmixer/reports/<report_name>/` физически лежат в core-дереве
   (namespace-пакет `dasmixer.reports`), но **им разрешено** импортировать
   `dasmixer.gui.components.report_form` внутри `try/except ImportError`.
   Обоснование (Developer): отчёты как таковые остаются доступны из core
   API/CLI без GUI; при этом полноценная жёсткая зависимость `core → gui`
   не возникает — единственная точка соприкосновения обёрнута в
   `try/except` и деградирует в `parameters = None`, когда `dasmixer-gui`
   не установлен. Правило #11 в AGENTS.md должно быть переформулировано
   (см. §7 — задача на обновление документации).

3. **Параметры отчёта — dataclass.** Базовый класс-маркер
   `ReportParams` — пустой dataclass, используемый только для типизации
   (`Generic`), содержательных общих полей не имеет.

### 1.2. Содержимое одного модуля-отчёта

**`params.py`** — dataclass параметров, наследник `ReportParams`:

```python
# dasmixer/reports/volcano_report/params.py
from __future__ import annotations
from dataclasses import dataclass, field
from dasmixer.api.reporting.report_params import ReportParams


@dataclass
class VolcanoReportParams(ReportParams):
    control_subset: str = ""
    exptl_subsets: list[str] = field(default_factory=list)
    lfq: tuple[str, str] = ("emPAI", "rel_value")
    stats_method: str = "Mann-Whitney"
    fdc: str = "BH"
    percent_to_calculate: int = 20
    fc_threshold: float = 1.5
    p_threshold: float = 0.05
    include_outliers: bool = False
    name_template: str = "{date} {time}"
```

Правила по dataclass'ам параметров:
- Поля 1:1 соответствуют текущим ключам словаря параметров конкретного
  отчёта (см. Приложение A с маппингом по каждому отчёту).
  Все текущие `params.get('x', default)` внутри `_generate_impl` заменяются
  на `params.x` (обращение к атрибуту dataclass) — значение по умолчанию
  теперь задаётся в самом dataclass field.
- Обязательное поле `name_template: str = "{date} {time}"` присутствует
  в **каждом** params-классе — это и есть механизм хранения
  пользовательского override шаблона имени (§4).
- Для отчётов без содержательных параметров (`ToolCoverageReport`,
  `SampleReport` не подпадает — есть параметры; фактически безпараметрических
  среди 7 нет, но общий шаблон предусмотрен) — минимальный class:
  ```python
  @dataclass
  class ToolCoverageReportParams(ReportParams):
      name_template: str = "{date} {time}"
  ```
- Сериализация в БД: `dataclasses.asdict(params_instance)` → `json.dumps(...)`.
  Desериализация для **повторной генерации из UI** — GUI формирует dataclass
  напрямую через форму (см. §3), поэтому `BaseReport` не обязан уметь
  реконструировать dataclass из JSON. Для **просмотра сохранённого отчёта**
  (`load_from_db`) `report_settings` остаётся обычным `dict`, полученным из
  `json.loads(...)` — используется только для отображения в шаблоне
  ("Report parameters" секция), полная типизация там не требуется.

**`form.py`** — GUI-форма, содержит:

### 1.3. Одно-файловый вариант (для плагинов)

Для совместимости с системой плагинов (`plugin_loader.py`,
`registry.register()` вызывается напрямую при импорте `.py`-файла) должна
сохраняться возможность определить весь отчёт в одном файле:

```python
# my_plugin_report.py
from dataclasses import dataclass
from dasmixer.api.reporting.base import BaseReport
from dasmixer.api.reporting.report_params import ReportParams
from dasmixer.api.reporting.registry import registry


@dataclass
class MyReportParams(ReportParams):
    threshold: float = 0.5
    name_template: str = "{date} {time}"


try:
    from dasmixer.gui.components.report_form import ReportForm, FloatSelector

    class MyReportForm(ReportForm):
        params_class = MyReportParams
        threshold = FloatSelector(default=0.5)

    _parameters = MyReportForm
except ImportError:
    _parameters = None


class MyReport(BaseReport):
    name = "My Plugin Report"
    parameters = _parameters
    params_class = MyReportParams

    async def _generate_impl(self, params: MyReportParams):
        ...


registry.register(MyReport)
```

Никаких изменений в `plugin_loader.py` не требуется — он уже просто
исполняет файл/пакет как модуль; паттерн "report_form по умолчанию внутри
одного файла" работает благодаря `try/except ImportError` в самом файле
плагина, а не благодаря особой поддержке лоадера.

## 3. Правки слоя форм (`report_form.py` core + GUI)

### 3.1. Core `ReportForm`/`ReportParamBase` (`api/reporting/report_form.py`)

Существенных изменений нет, кроме:
- Добавить в `ReportForm` (core) необязательный атрибут класса
  `params_class: type[ReportParams] | None = None`.
- `get_values()` остаётся возвращающим `dict` (для промежуточного
  использования/сериализации), но добавляется новый метод
  `get_params(self) -> ReportParams`:
  ```python
  def get_params(self) -> "ReportParams":
      if self.params_class is None:
          raise RuntimeError(f"{type(self).__name__} has no params_class set")
      values = self.get_values()
      return self.params_class(**values)
  ```
- `to_json()`/`from_json_str()` — без изменений в части сериализации
  словаря значений формы; **name_template хранится отдельно** от полей

### 4.3. Хранение `name_template`

Пользовательский override шаблона имени хранится **как обычное поле
dataclass params** — `name_template` есть в каждом `XxxParams` (см. §1.2).
Соответственно:
- Он сериализуется вместе со всеми остальными параметрами формы в
  `report_settings` JSON (при генерации, через `dataclasses.asdict`).
- Для **сохранения между сессиями до генерации** (аналог текущего
  `report_parameters` таблицы / `save_report_parameters()` /
  `get_report_parameters()`) — GUI-форма на карточке отчёта хранит поле
  "Name format" **отдельно от диалога параметров формы** (по решению
  Developer, п.4). Технически: `ReportItem` (GUI) держит собственный
  `ft.TextField` для Name format **на карточке** (не в диалоге), значение
  которого:
  - подгружается при `load_data()` вместе с остальными сохранёнными
    параметрами — из того же JSON, что и параметры формы (единый blob в
    `report_parameters`, ключ `name_template` хранится рядом с полями
    формы в одном словаре — т.е. `to_json()` формы **дополняется** полем
    `name_template`, взятым из отдельного текстового поля карточки, перед
    сохранением);
  - при построении `ReportParams` для генерации подставляется в
    итоговый dataclass (`params.name_template = card_name_template_field.value`)
    ПОСЛЕ `form.get_params()`, перезаписывая дефолт формы.

  Итого: JSON в `report_parameters` — это `{..поля формы.., "name_template": "..."}`,
  где `name_template` физически редактируется через контрол на карточке,
  но живёт в том же сериализованном словаре, что и остальные значения
  формы (упрощает код: не нужно две отдельных записи в БД).

### 4.4. Имя файла при экспорте

`{report_type_name}_{report_name}`, где:
- `report_type_name` — `self.name` (например `"Volcano Report (independent)"`);
- `report_name` — вычисленное значение (`get_report_name()` результат,
  сохранённый как `name` в БД при генерации; при экспорте
  свежезагруженного из БД отчёта берём `self._report_display_name`).

Санитизация: применяется `BaseReport._sanitize_filename()` **ко всей
результирующей строке целиком** (не по частям) — убираются символы,
недопустимые в NTFS (в первую очередь двоеточие из `{time}` формата
`ЧЧ:ММ`). Результат: `Volcano Report (independent)_260930 14.05` (если,
например, пользователь не менял разделители, но двоеточие заменяется на,
скажем, `-` или убирается — решение: заменять на `-`, т.к. полное удаление
двоеточия может склеить часы и минуты нечитаемо; уточнить у Developer при
код-ревью, дефолт — заменять `:` → `-`).

  (пустой `ToolCoverageReportParams`, пустая `ToolCoverageReportForm`).
  *Small.*
- **C2. Median Report** (`MedianReport`) — параметры: `subsets:
  list[str]`, `lfq: tuple[str,str]`, `include_outliers: bool`. *Small.*
- **C3. PCA Report** (`PCAReport`) — параметры: `subsets: list[str]`,
  `group_by: str`, `lfq: tuple[str,str]`, `show_labels: bool`,
  `top_n_proteins: int`, `include_outliers: bool`. *Medium* (файл большой,
  но правки механические).
- **C4. Sample Report** (`SampleReport`) — параметры: `max_samples: int`,
  `include_table: bool`, `chart_type: str`. *Small.*
- **C5. ToolMatch Report** (`ToolMatchReport`) — параметры: `tool1: str`,
  `tool2: str`. *Small.*
- **C6. Upset Report** (`UpsetReport`) — параметры: `subsets: list[str]`,
  `min_proteins: int`. Переименование модуля `upset.py` →
  `upset_report/report.py` (папка называется `upset_report` для
  единообразия с остальными — имя класса `UpsetReport` не меняется).
  *Small.*
- **C7. Volcano Report** (`VolcanoReport`) — параметры: `control_subset:
  str`, `exptl_subsets: list[str]`, `lfq: tuple[str,str]`,
  `stats_method: str`, `fdc: str`, `percent_to_calculate: int`,
  `fc_threshold: float`, `p_threshold: float`, `include_outliers: bool`.
  *Medium* (файл на 298 строк, но правки механические — только смена
  доступа к параметрам).

Каждая из C1–C7 — независимая параллельная задача (можно поручить
разным субагентам/раздельным PR), опирающаяся только на инфраструктуру
Блока A (готовый `ReportParams`, обновлённый `BaseReport`).
