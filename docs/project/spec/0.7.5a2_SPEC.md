## 1. Находки исследования, влияющие на дизайн

### 1.1 npysearch выполняет ЛОКАЛЬНОЕ выравнивание (проверено на npysearch-win 1.3.1 из venv проекта)

Эксперимент (БД: `P1`, `P3`; запросы длиной 14–20):

```
== minIdentity 1.0
A_exact_mid         P1 Q 1 20  T 9 28   identity 1.0     <- настоящее полное совпадение
C_last_mut(len 20)  P3 Q 1 14  T 9 22   identity 1.0     <- ЧАСТИЧНОЕ: покрыто 14 из 20 остатков
D_overhang(len 10)  P3 Q 1 6   T 17 22  identity 1.0     <- ЧАСТИЧНОЕ: 6 из 10
E_overhang(len 15)  P1 Q 5 15  T 1 11   identity 1.0     <- ЧАСТИЧНОЕ: 11 из 15
== minIdentity 0.8
E_overhang          P3 Q 5 15  T 1 11   identity 0.909   <- хвост запроса отрезан, identity считается по куску
```

Следствия:
- `Identity=1.0` в выдаче НЕ означает «весь запрос найден в белке». Текущий код (`protein_map.py`, ветка `identity == 1.0`) этого не учитывает и сохраняет такие хиты как точные (`matched_sequence = TargetMatchSeq` — укороченная).
- В новой реализации хит принимается только с учётом полного покрытия запроса. Эффективная идентичность считается как `eff_identity = NumMatches / len(query_sequence)`.
  - **Stage 1 (точное):** `NumMatches == qlen AND NumGaps == 0 AND NumMismatches == 0`.
  - **Stage 2:** `eff_identity >= min_protein_identity` (повторная фильтрация поверх npysearch); gaps допускаем (как сейчас).
- Побочный риск: частичные хиты занимают слоты `maxAccepts` (проект-настройка `max_blast_accept`, дефолт 5). Для коротких запросов, встречающихся во многих белках, полное совпадение может быть вытеснено. Фиксируем как известное ограничение, не меняем дефолты в этой версии.
- **Решение, требующее подтверждения Developer** (см. §10, п. 1): `eff_identity` вместо `Identity` из файла.

### 1.2 Прочие факты о npysearch

- API: `npy.blast(query, database, maxAccepts, maxRejects, minIdentity, alphabet='protein', outputToFile=False)`. `query`/`database` — dict или путь к fasta. Файлов-индексов, `threads`, `query_file=` и т.п. нет.
- `outputToFile=True` возвращает путь к CSV в CWD (`output_<YYYYmmdd_HHMMSS>.csv`, заголовок дописывается). Имя с точностью до секунды → два параллельных вызова в одной папке столкнутся. Мы вызываем строго последовательно и сразу переименовываем результат.
- Пустая выдача: CSV только с заголовком, `pandas.read_csv` читает его корректно (проверено, shape `(0, N)`).
- Длинные `QueryId` (в т.ч. с запятыми) возвращаются целиком (проверено). Но в новой схеме `QueryId` = целочисленный индекс (§3.2), поэтому это не нужно.
- Результат при `outputToFile=False` — dict списков; на больших объёмах его дорого пиклить из дочернего процесса. Используем `outputToFile=True` и читаем CSV в родительском процессе.
- Колонки: `QueryId, TargetId, QueryMatchStart, QueryMatchEnd, TargetMatchStart, TargetMatchEnd, QueryMatchSeq, TargetMatchSeq, NumColumns, NumMatches, NumMismatches, NumGaps, Identity, Alignment`. Координаты 1-based, закрытые интервалы.
- `TargetId` читать как `str` (id белка может быть числовым).

### 1.3 Ловушка миграции: индекс по новой колонке

`Project.initialize()` выполняет `executescript(CREATE_SCHEMA_SQL)` при КАЖДОМ открытии, до миграции (`core/lifecycle.py:42`). `CREATE TABLE IF NOT EXISTS` для существующей таблицы ничего не меняет, а `CREATE INDEX ... ON spectre(file_name)` в `CREATE_SCHEMA_SQL` упадёт на старом проекте (`no such column`) ещё до вызова `apply_migrations()`.

Решение: индекс `idx_spectre_file_name` НЕ включаем в `CREATE_SCHEMA_SQL`. Он создаётся: (а) в миграции `0.7.5`; (б) для нового проекта — отдельной константой `NEW_PROJECT_EXTRA_SQL` в `schema.py`, выполняемой в `initialize()` в ветке «создаём новую БД». (Остальные новые поля индексов не имеют.)

### 1.4 Прочие факты о коде

- `process_protein_map_row` отбрасывает `quality`, `longest_consec_run_rate`, `unconfirmed_ptms` из `MatchResult` — их нужно сохранить.
- `run_identification_queue` (`calculations/spectra/queue_runner.py`) считает `processed` по числу ВОЗВРАЩЁННЫХ строк, поэтому для прогресса батч-воркер должен возвращать строку на каждый вход (в т.ч. отклонённый).
- `add_peptide_matches_batch` вставляет построчно (`_executemany` закомментирован) — из-за «too many bad proteins» (FK при `src_file_protein_id`, которого нет в `protein`). Для нового пути нужен `executemany` с fallback.
- `get_idents_for_preferred` и `get_all_idents_for_preferred` используют подзапрос `GROUP BY identification_id` с независимыми `min()` — смешивает значения разных матчей и учитывает AA-substitution строки. Заменяется (§5).
- Корневой `pipeline.py` и CLI `calculate.py` устарели относительно `map_proteins` — не трогаем (E1).
- Потребители `peptide_match.matched_*` вне поиска: `plot_mixin.get_spectrum_plot_data`, `peptide_mixin.get_peptide_matches_with_spectra` + `ion_calculations.calculate_protein_metrics_internal`, `matching.py`, отчёты/экспорт через `get_joined_peptide_data` (аудит — задача T7.1).

### 3.1 Общая архитектура

Реализуется заменой тела `map_proteins()` в `calculations/peptides/protein_map.py`; новая логика раскладывается по новым модулям (все — чистый core, без `dasmixer.gui.*`):

```
calculations/peptides/
├── protein_map.py          # map_proteins() — оркестрация (сигнатура расширяется, см. 3.9)
├── protein_map_worker.py   # per-row worker (расширяется, см. 3.7)
├── fasta_export.py         # НОВЫЙ: выгрузка белков и запросов во временные файлы (3.3)
├── blast_runner.py         # НОВЫЙ: запуск npysearch в дочернем процессе (3.5)
├── blast_parse.py          # НОВЫЙ: разбор CSV, фильтры покрытия, fasta_start (3.6)
└── tmp_cleanup.py          # НОВЫЙ: очистка старых временных папок peptide_match (3.10)
```

Поток для каждого инструмента (tool):

```
Stage 0  подготовка:   белковая БД → dict (остаётся в памяти) → proteins.fasta [+ proteins_lic.fasta]
         per tool:     get_unique_sequences_for_search() → st1_plain_{tool_id}.fasta
Stage 1  simple:       blast(identity=1.0) → фильтр полного покрытия → запись в БД (пулом)
Stage 2  correction:   [de novo или AA subst] AND identity<1.0 → запрос из «ненайденных» → blast(identity)
Stage 3  processing:   spectra + SeqFixer + ион-покрытие → отбор → запись в БД
```

### 3.2 Структура уникальных последовательностей

Новый метод `PeptideMixin.get_unique_sequences_for_search(...)` в `project/mixins/peptide_mixin.py`.

```python
@dataclass
class SearchSequence:
    index: int                       # == QueryId в fasta
    search_sequence: str             # после преобразования I->L (если ilc), иначе canonical
    members: list[SearchMember]      # исходные канонические последовательности, слитые в один запрос

@dataclass
class SearchMember:
    canonical_sequence: str          # оригинал до I->L
    ident_ids: list[int]
```

Сигнатура:

```python
async def get_unique_sequences_for_search(
    self,
    tool_id: int,
    min_peptide_length: int,
    il_combinatorics: bool,
    sample_id: int | None = None,
    exclude_with_src_protein: bool = False,
) -> list[SearchSequence]:
```

SQL (фильтр длины и вычисление группы — в запросе, B2/B3):

```sql
SELECT i.canonical_sequence,
       group_concat(i.id) AS idlist
FROM identification i
[JOIN spectre s ON s.id = i.spectre_id
 JOIN spectre_file sf ON sf.id = s.spectre_file_id]       -- только если sample_id
WHERE i.tool_id = ?
  AND length(i.canonical_sequence) >= ?                    -- max(min_peptide_length, 4)
  [AND sf.sample_id = ?]
  [AND (i.src_file_protein_id IS NULL OR i.src_file_protein_id = '')]  -- exclude_with_src_protein
GROUP BY i.canonical_sequence
ORDER BY i.canonical_sequence
```

Python-постобработка:
1. Отбросить «однобуквенные» последовательности: `len(set(seq)) == 1` (GGGGGGGG).
2. Если `il_combinatorics`: `search_seq = seq.replace('I', 'L')`; последовательности с одинаковым `search_seq` сливаются в один `SearchSequence` с несколькими `members`.
3. Индексы присваиваются подряд с 0 после сортировки по `search_sequence`.
4. `idlist` разбирается `split(',')` → `list[int]`.

Важно: `group_concat` ограничен только `SQLITE_MAX_LENGTH`; при очень частых последовательностях строка длинная, но допустимая.

### 3.3 Выгрузка во временные файлы (`fasta_export.py`)

Рабочая папка: `config.get_tempdir('root') / 'peptide_match' / {project_stem} / {YYYYmmdd_HHMMSS}` (создаётся `mkdir(parents=True)`). Используется обычная (не large) временная папка. `project_stem` = `Path(project.path).stem` (если `project.path is None` → `'unnamed'`).

Функции:

```python
def make_work_dir(project_path: Path | None) -> Path
def write_proteins_fasta(proteins: dict[str, str], path: Path, il_combinatorics: bool = False) -> None
def write_queries_fasta(seqs: list[SearchSequence], path: Path) -> None
```

Правила:
- Запись — потоковая (построчно), НЕ через `npysearch.write_fasta` (он держит всё и не нужен). Формат `>{id}\n{sequence}\n`.
- `proteins.fasta`: ВСЕ белки со `sequence IS NOT NULL` (как `get_protein_db_to_search()`); исходный словарь `{protein_id: sequence}` остаётся в памяти — он нужен в Stage 1 для проверки I/L (3.6) и в Stage 3.
- `proteins_lic.fasta` — создаётся только если хотя бы у одного инструмента включён I/L; в нём `sequence.replace('I', 'L')`.
- `protein_id` с символами пробела/`>` в заголовке: npysearch берёт ID до первого пробела; заменяем пробельные символы в ID на `_`? НЕТ — ID должны совпадать с `protein.id`. Проверка в `write_proteins_fasta`: если ID содержит пробел или `>`, бросаем `DasmixerException` с понятным сообщением (в БД такие ID появиться не должны, но защищаемся).
- Запрос `st1_plain_{tool_id}.fasta` (имя из требований — оставляем независимо от I/L); для Stage 2 — `st2_{tool_id}.fasta`.

### 3.4 Stage 1 — простой поиск (identity = 1.0)

Параметры: `maxAccepts = max_blast_accept` (проект-настройка, дефолт 5), `maxRejects = max_blast_reject` (дефолт 16), `minIdentity = 1.0`, `alphabet='protein'`.

База: `proteins_lic.fasta` если у инструмента `leucine_combinatorics`, иначе `proteins.fasta`.

Обработка результата (в родительском процессе, `blast_parse.py`):
1. Читаем CSV в `pandas` с `dtype={'QueryId': int, 'TargetId': str}`, `usecols` — только нужные колонки.
2. Берём `qlen[index] = len(search_sequence)` из списка `SearchSequence`.
3. Оставляем строки с `NumMatches == qlen AND NumGaps == 0 AND NumMismatches == 0` (полное покрытие запроса; см. §1.1).
4. Для каждой строки и каждого `member` соответствующего `SearchSequence`:
   - `fasta_start = TargetMatchStart` (1-based, «номер аминокислоты в белке, с которой начинается последовательность»);
   - если у инструмента ilc: подпоследовательность оригинального белка `proteins[protein_id][fasta_start-1 : fasta_start-1+qlen]`; `correction = 'ilc'` если она НЕ равна `member.canonical_sequence` (т.е. реально потребовалась замена I/L), иначе `None`;
   - `matched_sequence` — подпоследовательность оригинального белка (всегда берём её, а не `TargetMatchSeq`, т.к. в lic-режиме `TargetMatchSeq` содержит L вместо I);
   - для каждого `ident_id` из `member.ident_ids` формируется строка `peptide_match`.
5. `unique_evidence = 1`, если число различных `protein_id` для данного `ident_id` равно 1, иначе 0 (после дедупликации по `(ident_id, protein_id, fasta_start)`).

Запись строки Stage 1 (B5):

| Поле | Значение |
|---|---|
| `protein_id`, `identification_id`, `matched_sequence` | см. выше |
| `identity` | `1.0` |
| `substitution` | `0` |
| `fasta_start` | `TargetMatchStart` |
| `correction` | `'ilc'` или NULL |
| `unique_evidence` | см. выше |
| остальные (`matched_ppm`, `matched_theor_mass`, `matched_coverage_percent`, `matched_peaks`, `matched_top_peaks`, `matched_ion_type`, `matched_sequence_modified`, `lcrr`, `quality`, `unconfirmed_ptms`) | NULL |

Пул записи: накапливаем строки; при достижении `config.protein_mapping_batch_size` (по числу строк `peptide_match`) → `add_peptide_matches_batch` (новый вариант на `executemany`, см. 3.8) + `project.save(checkpoint=True)`. Остаток — в конце этапа.

Если для инструмента нужен Stage 2/3, сохраняем `found_indexes: set[int]` — индексы `SearchSequence`, получившие хотя бы один принятый (полное покрытие) хит.

### 3.5 Запуск npysearch (`blast_runner.py`) — дочерний процесс (B11)

```python
def _blast_worker(query_path: str, db_path: str, work_dir: str,
                  max_accepts: int, max_rejects: int, min_identity: float,
                  result_name: str) -> str:
    """Executed in a child process."""
    import os, npysearch as npy
    old = os.getcwd()
    os.chdir(work_dir)
    try:
        out = npy.blast(query_path, db_path, maxAccepts=max_accepts,
                        maxRejects=max_rejects, minIdentity=min_identity,
                        alphabet='protein', outputToFile=True)
        final = os.path.join(work_dir, result_name)
        os.replace(out, final)           # out is relative to cwd
        return final
    finally:
        os.chdir(old)

async def run_blast(...) -> Path:
    loop = asyncio.get_running_loop()
    return Path(await loop.run_in_executor(executor, _blast_worker, ...))
```

- Один общий `ProcessPoolExecutor(max_workers=1)` на весь запуск `map_proteins` (создаётся в начале, закрывается в `finally`). Один воркер — потому что npysearch однопоточный, а имена выходных файлов имеют секундное разрешение.
- Все пути — абсолютные (`Path.resolve()`).
- Имена результатов: `st1_result_{tool_id}.csv`, `st2_result_{tool_id}.csv` (не удаляются).
- Между этапами проверяем `stop_check()`. Прерывание внутри `blast` невозможно (нативный вызов): остановка срабатывает после его завершения.
- Если `npy is None` → `ImportError` с прежним текстом (проверка остаётся в `map_proteins`).

### 3.6 Stage 2 — поиск со сниженной точностью

Условие запуска: `(denovo_correction OR save_aa_substitutions) AND min_protein_identity < 1.0` (из требований).

Запрос:
1. `remaining = [s for s in seqs if s.index not in found_indexes]`. Если пусто — Stage 2 пропускается целиком.
2. Файл `st2_{tool_id}.fasta` с теми же индексами (индексы НЕ перенумеруются — это упрощает слияние).
3. `blast(minIdentity = min_protein_identity)`, база — как в Stage 1.

Фильтрация результата (`blast_parse.py`):
- считаем `eff_identity = NumMatches / qlen` (§1.1);
- оставляем строки с `eff_identity >= min_protein_identity` и `eff_identity < 1.0` (полные совпадения не должны появляться — они уже обработаны);
- по каждому `(index, protein_id)` оставляем строку с максимальной `eff_identity` (затем с минимальным `NumGaps`);
- по каждому `index` оставляем только строки с максимальной `eff_identity` (аналог `_filter_worse_idents`); при этом дедупликация по `ident_id` выполняется на Stage 3 после пересчёта.

Выход Stage 2 — список `Candidate(index, ident_id, protein_id, fasta_start, target_match_seq, query_match_seq, eff_identity)` — по одному кандидату на пару `(ident_id, protein_id)`.

### 3.7 Stage 3 — обработка со спектрами

Выполняется для кандидатов Stage 2. Запуск: `denovo_correction OR save_aa_substitutions` (иначе Stage 2 и 3 не нужны).

Порядок:
1. Идентификации разбиваются на пачки `batch_size = config.identification_processing_batch_size`; для каждой пачки читаются спектры `get_spectra_for_identification_ids` и нужные поля идентификации (`sequence`, `canonical_sequence`, `ppm`, `intensity_coverage`, `ions_matched`, `top_peaks_covered`, `lcrr`, `quality`, `isotope_offset`, `override_charge`, `charge`, `score`, `pepmass`).
2. Каждый кандидат отправляется в `ProcessPoolExecutor(max_workers=worker_count)` через `process_protein_map_row` (расширенный).
3. Прогресс (см. 3.9) обновляется по числу обработанных кандидатов; запись результатов — в процессе, пулом `protein_mapping_batch_size`.

#### Расширение `process_protein_map_row`

Дополнительно к текущему результату возвращает `lcrr = match_result.longest_consec_run_rate`, `quality = match_result.quality`, `unconfirmed_ptms = match_result.unconfirmed_ptms`, а также `fasta_start` (передаётся из `row_dict` и возвращается как есть). Прочие поля — как сейчас.

Новый вход в `row_dict`: `ident_lcrr`, `ident_quality` (текущие значения идентификации), `denovo_correction: bool`, `score` (B10, чтобы `min_score` в `_ident_passes_tool_thresholds` начал работать).

#### Логика принятия (замена `_check_correction_criteria`, B8/B9)

Критерии (ключи в `Tool.settings['match_correction_criteria']`): `'ppm'`, `'lcrr'`, `'quality'`, `'intensity_coverage'`. Для каждого критерия «улучшение» (строго, с NaN-защитой):

| Критерий | Улучшение |
|---|---|
| `ppm` | `abs(match.ppm) < abs(ident.ppm)` |
| `lcrr` | `match.lcrr > ident.lcrr` |
| `quality` | `match.quality > ident.quality` |
| `intensity_coverage` | `match.intensity_percent > ident.intensity_coverage` |

Если `ident.<метрика>` NULL (метрика не рассчитана) — считаем, что любое рассчитанное значение match её улучшает.

Решение:
```
if denovo_correction AND (criteria is empty OR any criterion improved):
    result.correction = 'denovo'; result.substitution = 0   -> сохранить
elif save_aa_substitutions AND ident passes tool thresholds:
    result.correction = None;     result.substitution = 1   -> сохранить
else:
    отклонить
```

(Старые ключи `ions_matched`, `top10_ions_matched` игнорируются — отсутствуют в таблице критериев.)

`matched_ppm` сохраняется как абсолютное значение (как сейчас) — это совместимо с `abs()` в фильтрах (D1).

После пересчёта для каждой `ident_id` оставляем только записи с максимальным `identity`, затем `drop_duplicates(['protein_id'])`; приоритет: `denovo` > `substitution`.

> Примечание для разработчика: `match_correction_criteria` по умолчанию в GUI `['ppm','intensity_coverage']`; core-дефолт `[]` выравниваем на тот же `['ppm','intensity_coverage']` (T3.7).

### 3.8 Запись `peptide_match` и схема ключей

Расширяем `PeptideMixin.add_peptide_matches_batch` (колонки `lcrr, unconfirmed_ptms, quality, fasta_start, correction`; `unique_evidence`, `substitution` как раньше). Для Stage 1 добавляем `add_peptide_matches_batch_fast(matches_df)` — `executemany` в одной транзакции без построчного fallback; перед этим `map_proteins` фильтрует `protein_id`, отсутствующие в `protein` (set из словаря белков), чтобы не ловить FK-ошибку. Метод старый остаётся для обратной совместимости.

### 3.9 Сигнатура и прогресс `map_proteins`

Сигнатура не ломается; `progress_callback` расширяется:

```python
progress_callback: Callable[[ProteinMapProgress], None] | None
```

```python
@dataclass
class ProteinMapProgress:
    tool_index: int            # 0-based
    tool_count: int
    stage: str                 # 'prepare' | 'simple' | 'save_simple' | 'correction' | 'processing'
    message: str               # готовая строка из требований
    fraction: float            # 0..1 для ВСЕГО запуска (с учётом всех инструментов)
    processed: int | None = None
    total: int | None = None
```

Строки `message` (формат из требований):
- `Create sequence databases...`
- `Simple search (identity=1.0)...`
- `Saving simple search results ({uq_sequences_no} unique sequences)...`
- `Correction search (identity={identity})...`
- `Processing corrected sequences ({processed} of {total})...`

Доли внутри одного инструмента:
- Stage 2/3 не выполняются (identity = 1.0 или нет флагов): три этапа по 1/3.
- Иначе: первые четыре этапа по 15% (суммарно 60%), `processing` — линейно от 60% до 100% по `processed/total`.
- Для N инструментов: `fraction = (tool_index + local_fraction) / tool_count`.
- «Create sequence databases...» относится к общему этапу подготовки (файлы белков), занимает первый слайс первого инструмента.

Старый вызов `progress_callback(processed, total)` больше не поддерживается (callback принимает один аргумент). GUI и CLI-обёртка (последняя — вне scope) обновляются в T6.x.

## 4. Core: `source_ppm` (A3)

`IdentificationMixin.put_identification_data_batch`:

```sql
UPDATE identification SET
    source_ppm = CASE
        WHEN source_ppm IS NULL AND ppm IS NOT NULL
             AND (? IS NULL OR abs(ppm - ?) > 1e-9)
        THEN ppm ELSE source_ppm END,
    sequence = ?, ppm = ?, ...        -- остальное без изменений
WHERE id = ?
```

(SQLite вычисляет правые части UPDATE по старой строке, поэтому `ppm` в CASE — прежнее значение.) Правила:
- `source_ppm` записывается один раз — при первом ИЗМЕНЕНИИ ppm (новое значение отличается от старого более чем на 1e-9 либо стало NULL). Повторные пересчёты и пересчёты без изменений (`trust_ppm`) `source_ppm` не трогают.
- Параметры порядка: `new_ppm` передаётся дважды (для `? IS NULL` и `abs(ppm - ?)`).
- Ключ `ppm` в `data_rows` отсутствует/`None` трактуется как «новое = NULL».

`IdentificationMixin.clear_calculations`: `ppm = source_ppm` вместо `ppm = NULL`; затем `source_ppm = NULL`. В выражении `UPDATE` порядок присваиваний не важен (старые значения), но обе колонки должны быть в одном `SET`.

Добавить `i.source_ppm` в SELECT `get_joined_peptide_data` (скрытая колонка, §7.3).

## 5. Core: preferred selection (§ «Доработки в логике preferred selection»)

### 5.1 Запросы `get_idents_for_preferred` / `get_all_idents_for_preferred` (`identification_mixin.py`)

Убираем подзапрос `GROUP BY identification_id`. Новый JOIN — только de novo-варианты:

```sql
FROM identification i
LEFT JOIN spectre s ON i.spectre_id = s.id
LEFT JOIN peptide_match m
       ON m.identification_id = i.id AND m.correction = 'denovo'
```

Фильтры (каждый — по логике «исходное значение ИЛИ значение скорректированного совпадения»):

| Фильтр | Условие |
|---|---|
| PPM | `(abs(i.ppm) <= :max_ppm OR (m.correction='denovo' AND abs(m.matched_ppm) <= :max_ppm))` |
| Intensity coverage | `(i.intensity_coverage >= ? OR (m.correction='denovo' AND m.matched_coverage_percent >= ?))` |
| Ions matched | `(i.ions_matched >= ? OR (m.correction='denovo' AND m.matched_peaks >= ?))` |
| Top peaks | `(i.top_peaks_covered >= ? OR (m.correction='denovo' AND m.matched_top_peaks >= ?))` |
| Quality (если задан) | `((i.quality IS NOT NULL AND i.quality >= ?) OR (m.correction='denovo' AND m.quality IS NOT NULL AND m.quality >= ?))` |
| LCRR (если задан) | аналогично, `m.lcrr` |
| Unconfirmed PTMs (если задан) | `((i.unconfirmed_ptms IS NOT NULL AND i.unconfirmed_ptms <= ?) OR (m.correction='denovo' AND m.unconfirmed_ptms IS NOT NULL AND m.unconfirmed_ptms <= ?))` |
| score, fdr, длина `canonical_sequence`, `s.peaks_count`, `s.spectre_file_id`, `i.tool_id` | только `i.*` / `s.*`, без OR-ветки |

Строки с `m.correction IS NULL` (нет denovo-совпадения) проходят по `i.*`-ветке; строки с `substitution=1` и `correction='ilc'` на preferred не влияют (JOIN их исключает).

SELECT возвращает «эффективные» значения (C1):

```sql
i.id, i.spectre_id, i.tool_id, i.score, i.fdr, s.spectre_file_id,
CASE WHEN m.id IS NOT NULL THEN abs(m.matched_ppm) ELSE abs(i.ppm) END                      AS eff_abs_ppm,
CASE WHEN m.id IS NOT NULL THEN m.matched_coverage_percent ELSE i.intensity_coverage END    AS eff_intensity_coverage
```

(плюс исходные `i.ppm`, `i.intensity_coverage`, `i.lcrr`, `i.unconfirmed_ptms` для обратной совместимости потребителей).

Несколько denovo-совпадений у одной идентификации (разные белки) дают несколько строк. Метод сам сворачивает их в одну строку на `i.id`: берётся строка с наименьшим `eff_abs_ppm` (для критерия ppm) / наибольшим `eff_intensity_coverage` (для intensity) — сортировка производится по обоим ключам, выбор по обоим одновременно не нужен, поэтому метод принимает параметр `criterion: Literal['ppm','intensity']` и оставляет лучшую строку по нему. Для `get_all_idents_for_preferred` — тот же принцип, без фильтров.

## 10. Допущения, требующие подтверждения Developer

1. **(важно) `Identity` из npysearch.** Проверено экспериментально (§1.1): выравнивание локальное, `Identity=1.0` бывает у частичного покрытия запроса (запрос 20 aa, совпали 14 → identity 1.0). Предлагаю считать точным совпадением только `NumMatches == len(query) AND NumGaps == 0`, а в Stage 2 — `eff_identity = NumMatches / len(query)`. Иначе в БД попадут укороченные `matched_sequence` как «точные». *Если не согласны — укажите, как трактовать.*
2. **Preferred: OR по каждому фильтру независимо** (как в требованиях). Возможна ситуация, когда идентификация проходит PPM по исходному значению, а покрытие — по значению denovo-совпадения. Альтернатива (строже): все метрики из одного варианта — «исходный набор» либо «denovo-набор». По умолчанию реализуем как в требованиях.
3. **`min_score` в `get_joined_peptide_data`** добавляется попутно (иначе `TypeError`, если GUI передаст фильтр). Если нужно строго без побочных правок — исключаем из T4.1.
4. **`source_ppm`** пишется только при реальном изменении `ppm` (§4). Если нужно писать всегда при первом пересчёте — упрощаем CASE.
5. Строки Stage 1 содержат NULL в `matched_*`; места, где они читались как числа, в аудите T7.1 получают fallback на значения идентификации.

> 1. Подтверждаю
> 2. Да, независимо, всё верно
> 3. Да
> 4. Только при пересчёте
> 5. Верно
