## 0. Обзор

Три связанные задачи вокруг проблемы «на образец привязано несколько `spectre_file`»:

| # | Задача | Затронутые пакеты |
|---|---|---|
| A | Импорт identification-файлов: авто-привязка к правильному `spectre_file` при batch-импорте, когда у образца их несколько | `dasmixer-core`, `dasmixer-cli`, `dasmixer-gui` |
| B | Экспорт MGF: флаг «Replace SCANS with Spectre ID» | `dasmixer-core`, `dasmixer-gui` |
| C | Экспорт MGF: режим «Merge MGF» (One file / By sample / By Spectre file) + флаг «Add timestamp to file name» | `dasmixer-core`, `dasmixer-gui` |

**Мотивация (контекст, не требует действий в коде):** `identification_file.spectre_file_id`
обязателен и используется для построения маппинга `seq_no/scans → spectre_id`
(`get_spectra_idlist(spectra_file_id, ...)`) при импорте идентификаций. Сейчас во всех
batch-путях (`CLI ident-pattern`, `CLI ident-file` без `--spectra-file-id`, GUI pattern-импорт,
GUI stacked-импорт, legacy `samples_tab`) выбор `spectre_file` для образца с несколькими
файлами — «первый по `id`» (`ORDER BY id LIMIT 1` / `.iloc[0]`), без проверки соответствия
содержимому. Это может приводить либо к нулевому импорту (диапазоны `seq_no`/`scans` не
пересекаются), либо к тихой порче данных (пересекающиеся `seq_no`/`scans` → идентификации
привязываются к чужим спектрам). Задача A вводит детерминированную авто-привязку по имени
файла вместо произвольного выбора по `id`.

Задачи B и C — независимая доработка экспорта MGF, которая даёт администратору инструмент для
предотвращения той же проблемы «на входе»: раздельный экспорт по `spectre_file` и/или запись
`spectre.id` в поле `SCANS`, что делает обратное сопоставление однозначным средствами внешнего
инструмента (без необходимости менять логику импорта — реимпорт по `spectre_id` **не
реализуется**, это осознанное решение, см. раздел 1).

Задачи независимы друг от друга, реализуются в любом порядке.

## 1. Согласованные решения (из диалога с разработчиком)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Механизм авто-привязки identification-файла к `spectre_file` при batch-импорте | Сопоставление **по имени**: сортировка identification-файлов и `spectre_file` образца по `basename(path)`, позиционная пара (i-й ↔ i-й). Не эвристика по паттерну, не «просто первый файл». |
| 2 | Ключ сортировки | `(sample.name, basename(path))`. Поскольку сопряжение всегда идёт **внутри одной группы-образца**, `sample.name` в паре константа — реально решает `basename`; `sample.name` используется только для группировки/порядка обработки. |
| 3 | Несовпадение количества (identification-файлов больше, чем `spectre_file`, или наоборот) | Лишние identification-файлы **пропускаются с предупреждением**, не импортируются. Не зацикливаем на последнем, не прерываем весь импорт ошибкой. |
| 4 | Где в GUI реализовать | Только **pattern-диалог** (`ImportPatternDialog`, кнопка Preview Files) — основной batch-путь. `ImportStackedDialog`, `ImportSingleDialog`, legacy `samples_tab.py`, панельный импорт (`manage_samples_view`, уже использует явный `fixed_spectra_file_id`) — **вне scope**, не трогаем. |
| 5 | Ручной выбор в GUI | В pattern-диалоге на каждой строке файла — выпадающий список `Spectre file` со всеми `spectre_file` образца этой строки; значение по умолчанию — авто-пара, доступна ручная замена. |
| 6 | CLI | Та же логика авто-привязки по имени, **без возможности ручного выбора** (batch-режим, неинтерактивный). |
| 7 | Реимпорт identification-файлов, полученных из MGF с `SCANS=spectre.id` | **Не реализуем.** Флаг «Replace SCANS with Spectre ID» — экспорт-only фича, реимпорт с маппингом по `spectre_id` не подразумевается и не входит в scope. |
| 8 | Именование файлов в режиме «By Spectre file» | `{sample_name}_{spectre_file_id}` (+ таймстемп-суффикс, если включён) — id вставляется **перед** таймстемпом. |
| 9 | Режим «One file» | Объединяет спектры **всех** выбранных в форме экспорта образцов в один MGF-файл, имя `dasmixer_mgf` (+ таймстемп-суффикс, если включён). В этом режиме `zip_all` и `zip_each` обязаны давать идентичный результат (см. раздел 4.3). |
| 10 | Флаг «Add timestamp to file name» | Новый чекбокс на форме экспорта MGF. При `No` — таймстемп не добавляется **нигде** в именах выходных файлов ни в одном из режимов Merge MGF (включая имя общего zip-контейнера при `zip_all`). |

## 2. Задача A — авто-привязка identification-файла к `spectre_file`

### 2.1. Текущее состояние (контекст)

Выбор `spectre_file` «первый по `id`», без проверки соответствия содержимому, происходит в:

| Точка входа | Механизм | Место |
|---|---|---|
| CLI `ident-file` (без `--spectra-file-id`) / `ident-pattern` | `SELECT id FROM spectre_file WHERE sample_id=? ORDER BY id LIMIT 1` | `dasmixer-cli/src/dasmixer/cli/commands/import_data.py:282-291` |
| GUI pattern-импорт | `spectra_files.iloc[0]['id']` | `dasmixer-gui/src/dasmixer/gui/views/tabs/samples/import_handlers.py:249` |
| GUI stacked-импорт | `spectra_files.iloc[0]['id']` | `import_handlers.py:468` (вне scope, не трогаем) |
| Legacy `samples_tab.py` | `spectra_files.iloc[0]['id']` | `samples_tab.py:1356` (вне scope, не трогаем) |
| Панельный импорт | `fixed_spectra_file_id` передаётся явно с панели конкретного `spectre_file` | `manage_samples_view.py:709-722` (уже корректно, не трогаем) |

`identification_file.spectre_file_id` используется для построения маппинга через
`get_spectra_idlist(spectra_file_id, by=parser.spectra_id_field)` — маппинг ограничен ОДНИМ
`spectre_file`, поэтому привязка к неверному файлу даёт либо 0 совпадений (`pd.merge(how='inner')`
отбрасывает всё), либо ложные совпадения при пересекающихся `seq_no`/`scans`.

`sample.name` — `UNIQUE NOT NULL` в схеме (`schema.py:40`), коллизий имён образцов нет.
`get_spectra_files(sample_id)` (`spectra_mixin.py:55`) уже возвращает `id`, `path`,
`sample_name` — новый метод в core не нужен, сортировка выполняется в Python на стороне
вызывающего кода.

### 2.2. T1 — Core: утилита сопряжения

**Новый файл:** `dasmixer-core/src/dasmixer/utils/ident_spectra_pairing.py`

```python
"""Позиционное сопряжение identification-файлов со spectre_file образца по имени."""

from pathlib import Path


def resolve_ident_to_spectra_mapping(
    ident_paths: list[str],
    spectra_files: list[dict],  # [{"id": int, "path": str}, ...] — spectre_file ОДНОГО образца
) -> tuple[dict[str, int], list[str]]:
    """
    Сортирует identification_paths и spectra_files по basename(path), сопрягает позиционно
    (i-й identification-файл -> i-й spectre_file). Лишние identification-файлы (когда их
    больше, чем spectre_file) возвращаются в unmatched.

    Returns:
        (mapping {ident_path: spectra_file_id}, unmatched_ident_paths)
    """
    ident_sorted = sorted(ident_paths, key=lambda p: Path(p).name)
    spectra_sorted = sorted(spectra_files, key=lambda s: Path(s["path"]).name)

    mapping: dict[str, int] = {}
    unmatched: list[str] = []
    for i, ident_path in enumerate(ident_sorted):
        if i < len(spectra_sorted):
            mapping[ident_path] = int(spectra_sorted[i]["id"])
        else:
            unmatched.append(ident_path)
    return mapping, unmatched
```

Используется идентично в CLI и GUI (единая логика, требование п.6 раздела 1).

### 2.3. T2 — CLI (`dasmixer-cli/src/dasmixer/cli/commands/import_data.py`)

**`_import_ident_file_internal`** (строки 246-348): в ветке `if spectra_file_id is None:`

детерминированный выбор «первый по имени» вместо «первый по `id`» (безопасное поведенческое
изменение, при одном `spectre_file` ничего не меняется).

**`ident_pattern`** (строки 351-434): перед основным циклом импорта — новый pre-pass:

1. Нормализовать `sid` так же, как в текущем цикле (`if not sid: sid = file_path.stem`) —
   **до** группировки, чтобы ключи группы совпадали с ключами в основном цикле.
2. Сгруппировать нормализованный список файлов по `sid` (`defaultdict(list)`).
3. Открыть проект **один раз** (`async with Project(...)`), для каждой группы:
   `sample = await project.get_sample_by_name(sid)`; если найден —
   `sf_df = await project.get_spectra_files(sample_id=sample.id)` →
   `resolve_ident_to_spectra_mapping(...)` → аккумулировать `spectra_map` (path→id) и
   `unmatched` (set путей).
4. Основной цикл импорта — по нормализованному списку `(file_path, sid)`:
   - если `str(file_path)` в `unmatched` → `typer.echo("  Warning: ... no spectre_file pair (more identification files than spectre_file), skipped")`, `continue` (не вызывать `_import_ident_file_internal`);
   - иначе — `spectra_file_id=spectra_map.get(str(file_path))` (может быть `None`, если
     сэмпл не найден или без `spectre_file` вовсе — в этом случае старая обработка ошибки
     внутри `_import_ident_file_internal` (строки 267-291) сработает как раньше).

Итоговое количество открытий проекта увеличивается на одно (pre-pass) — существующий код и
так открывает проект заново на каждый файл в цикле (`_import_ident_file_internal`), это не
регрессия производительности относительно текущего поведения.

## 4. Задача C — режим «Merge MGF» + флаг «Add timestamp to file name»

### 4.1. Текущее поведение (контекст)

`export_mgf` (`mgf_export.py:242-371`) всегда экспортирует **по образцу**: для каждого
`sample_id` из `sample_ids` — объединяет спектры **всех** его `spectre_file`
(`SELECT id FROM spectre_file WHERE sample_id = ?`, строки 297-307) в один выходной MGF,
имя `{sample_name}_{timestamp}.mgf` (строка 318). Это и есть корень потенциальной путаницы
`SCANS`/`seq_no` при пересечении диапазонов между несколькими `spectre_file` одного образца
(раздел 0). Режим «By Spectre file» даёт администратору способ не объединять данные вовсе.

### 4.2. T8 — `dasmixer-core/src/dasmixer/api/export/shared_state.py`

Добавить в `ExportTabState`:
```python
mgf_merge_mode: str = "by_sample"   # "one_file" | "by_sample" | "by_spectre_file"
mgf_add_timestamp: bool = True
```

### 4.3. T9 — `dasmixer-core/src/dasmixer/api/export/mgf_export.py`

**Новая функция** `_build_export_units(project, sample_ids, merge_mode)` →
`list[dict]` с полями `label` (для progress_callback), `base_name` (без расширения и
таймстемпа), `sf_ids` (список `spectre_file.id` для объединения в юнит):

- `merge_mode == "by_sample"` (текущее поведение): один юнит на каждый `sample_id` из
  `sample_ids`; `sf_ids` = все `spectre_file` образца; `base_name = _sanitize(sample.name)`.
  Образец без `spectre_file` — юнит пропускается (как сейчас, строки 300-305).
- `merge_mode == "by_spectre_file"`: для каждого `sample_id` — по одному юниту **на каждый**
  его `spectre_file` (без объединения); `sf_ids = [sf_id]`;
  `base_name = f"{_sanitize(sample.name)}_{sf_id}"` (id — перед таймстемп-суффиксом, п.8
  раздела 1). Сортировка `spectre_file` внутри образца — по `id` (детерминированный порядок
  прогресса, объединения нет — порядок не влияет на результат).
- `merge_mode == "one_file"`: **один** юнит на весь вызов, `sf_ids` = объединение
  `spectre_file` **всех** `sample_ids`; `base_name = "dasmixer_mgf"`.

**`export_mgf(...)`**: добавить параметры `merge_mode: str = "by_sample"`,
`add_timestamp: bool = True` (плюс `replace_scans` из задачи B). Изменения по телу:

```python
ts_suffix = f"_{timestamp}" if add_timestamp else ""
zip_all_path = os.path.join(output_dir, f"dasmixer_mgf{ts_suffix}.zip")
...

total = len(units)
for idx, unit in enumerate(units):
    await progress_callback(idx / total if total else 0.0, f"Exporting: {unit['label']}")
    sf_ids = unit["sf_ids"]
    spectrum_ids = await _get_spectrum_ids(project, sf_ids, by, tool_id)
    if not spectrum_ids:
        await progress_callback((idx + 1) / total if total else 1.0, f"Skipping {unit['label']} (no matching spectra)")
        continue
    base_name = f"{unit['base_name']}{ts_suffix}"
    # ... остальное тело (ветки compression) без изменений, используют base_name как раньше
```

Блок получения `sf_ids` через `SELECT id FROM spectre_file WHERE sample_id = ?` (старые
строки 296-307) и вызов `_get_sample`/сборка `sample_name` — удаляются, логика переезжает в
`_build_export_units`.

**Инвариант `zip_all` == `zip_each` при `merge_mode="one_file"`** (п.9 раздела 1): при
`one_file` в списке `units` ровно один элемент — обе ветки (`zip_all`: один `ZipFile` на весь
вызов; `zip_each`: один `ZipFile` на файл) физически создают по одному zip-архиву с одним
MGF-файлом внутри. Специального кода для этого инварианта не требуется — он следует
автоматически из того, что `len(units) == 1`; в комментарии над `_build_export_units`
зафиксировать это явно, чтобы не было соблазна поставить `assert` или спецкейс.
