## LASTRUN_VERSION и расширение .CSV-файла с переименованиями

При инициализации GUI создаём файл LASTRUN_VERSION в папке конфигурации. Содержит только значение APP_VERSION.

С файлом возможны два сценария:
1. Файл сущестует и содержит текущую версию:
   - Ничего не делаем, продолжаем штатную инициализацию
2. Файл отсутствует или содержит отличную от текущей версию:
   - Читаем файл конфигурации import_ptm_renames.csv (создание файла при отсутствии должно происходить ДО проверки LASTRUN_VERSION), также берём его версию из исходного кода. Задача: сопоставить эти две версии и дополнить заменами из новой версии. Добавляем те, которых в текущей версии файла нет по совпадению сразу двух параметров: parser, source.
   - Схожая операция для файла all_ptm_config.csv, добавляем новые при отсутствии значения name в исходном файле.
   - Обновляем LASTRUN_VERSION, сохраняя текущую APP_VERSION

Суть задачи: при добавлении в сборку новых PTM и новых парсеров, необходимо добавить обновления текущей версии, при этом не потеряв то, что добавлено пользователем. 

Примечание: проверку на версию выше текущей не реализуем, т.к. сценарий редкий, логка работы с конфигурацией при отличии версий при этом допустима.

Для CLI: добавляем команду update-ptm-list, при вызове которой выполняется описанная выше логика. При других вызовах CLI обновление не делаем

## Импорт идентификаций из MZTab

Реализуем новый парсер для MZTab-файлов, используем pyteomics.mztab для импорта, строим его как субкласс dasmixer-core/src/dasmixer/api/inputs/peptides/base.py.

Читаем только секции MTD (metadata) и PSM, остлаьные нас не интересуют.

Реализуем сразу с функционалом множественного импорта (один файл на несколько исходных файлов). Используем привязку через metadata ms_run[N]-location: там путь с названием для исходного файла

Функционал импорта идентификаций белков также реализуем, реализуем по аналогии с SimpleTableParser, т.е. собираем список из таблицы PSM, не смотрим на файл с белками.

Важный момент - мэппинг к spectre file через идентификацию в столбце spectre_ref у PSM. Здесь есть своя специфика и возможны разные варианты. если указание идёт через index - используется мэппинг по seq_no

Парсер (этот и следующие описанные) регистрируем в списке парсеров идентификаций

Для понимания задачи, есть:

- спецификация формата: docs/project/INTERNAL_EXAMPLES/mztab/mzTab_format_specification.md. Заголовки и разметку можно игнорировать, не идеальная конвертация из PDF 
- docs/project/INTERNAL_EXAMPLES/mztab/SINGLE_FILE_EXAMPLE.mzTab - пример mzTab-файла для одного файла спектров
- docs/project/INTERNAL_EXAMPLES/mztab/MULTIFILE_EXAMPLE.mzTab - пример mzTab-файла для нескольких образцов
- docs/project/INTERNAL_EXAMPLES/mztab/CASANOVO_EXAMPLE.mztab - пример для CasaNovo, описан как отдельный парсер ниже.

ВАЖНО: файлы большого размера, используй pyteomics для чтения из них и подтверждения формата. Также для этих примеров у меня сейчас здесь нет соответствующих MGF, интеграционное тестирование реализовать не получится.

### Обработка модификаций

Список модификаций мы получаем из MTD-секции файла и дальше испольуем как список переименовывания, смешав при этом fixed и variable, их процессирование универсальное.

В mzTab допустимы два вида модификаций:
- UNIMOD: сыслка на UNIMOD DB. Может содержать описание в формате:
```
MTD variable_mod[1] [UNIMOD, UNIMOD:21, Phospho, ]
```

Для приведения к ProForma используем pyteomics:

```python
from pyteomics.mass import Unimod
u = Unimod() # Инициируется вне функции в начале процесса паринга, должен быть доступен через self.unimod
u.by_id(unimod_id)['title'] #где unimod_id - числовой идентификатор, для UNIMOD:21 это будет 21.
```

Второй тип модификаций обозначается CHEMMOD и не имеет модификатора, задаётся массой:
```
CHEMMOD:113.08406
```
В ProForma преобразуется напрямую в обозначение массы, напр. `[+113.08406]`

Ещё один тип задаётся с PSI-MOD ID через MOD: `MOD:00815`. Такие модификации просто транслируем в формат `[PSI-MOD:XXXXXXX]`

Определение канонической последоватлеьности для строки должно быть вынесено в отдельный метод для возможности переопределения в наследующих парсерах.

Логика по умолчанию вовлекает два параметра для каждой строки:
- sequence
- modifications

где sequence - это каноническая последовательность, а modifications - список модификаций в сложном формате. Вставлю описание из спецификации:

>Modifications or substitutions are modelled using a specific modification object with the
following format:
{position}{parameter}-[{modification or substitution identifier}|{neutral loss}]
The number of modification (or substitution) objects MUST correspond to the number of
identified modifications (or substitutions) on a given peptide or PSM. It is also expected that
modifications SHOULD be reported for proteins using the same format. However, it is
recognised that some export software may not be able to do this. If software cannot
determine protein-level modifications, “null” MUST be used. If the software has determined
that there are no modifications to a given protein “0” MUST be used.
>
>{position} is mandatory. However, if it is not known (e.g. MS1 Peptide Mass Fingerprinting),
‘null’ must be used Terminal modifications in proteins and peptides MUST be reported with
the position set to 0 (N-terminal) or the amino acid length +1 (C-terminal) respectively. This
object allows modifications to be assigned to ambiguous locations. Ambiguous positions can be reported
by separating the {position} and (optional) {cvParam} by an ‘|’ from the next position. Thereby,
it is possible to report reliabilities / scores / probabilities etc. for every potential location.
>
```
Here only the modification field is given:

3-MOD:00412, 8-MOD:00412            # TESTPEPTIDES with two known phosphorylation sites
3|4-MOD:00412, 8-MOD:00412          # First phosphorylation site can be either on S or T
3|4|8-MOD:00412, 3|4|8-MOD:00412    # Three possible positions for two phosphorylation sites
```
>{parameter} is optional. It MAY be used to report a numerical value e.g. a probability score
associated with the modification or location.
Reporting the first two possible sites for the phosphorylation with given probability score
Here only the modification field is given:
```
3[MS,MS:1001876, modification probability, 0.8]|4[MS,MS:1001876, modification probability, 0.2]-MOD:00412, 8-MOD:00412
```

Данные о вероятностях модификации при наличии, а также любые данные из квадратных скобок мы не сохраняем. Если для PTM указаны более одной позиции, "сбрасываем" её в unlocalized_modifications (не запоминаем варианты позиции).

Последоватлеьность собираем по следующей логике:
- Преобразуем каноническую последовательность из sequence к ProForma через pyteomics.proforma.parse, которая возвращает tuple из seq и params
- Прикрепляем модификации к соответствующим аминокислотам в seq вторым элементом tuple вместо None
- В Params заполняем n_term, c_term, unlocalized_modifications. Здесь помним, что величина или None, или список, даже если из одного элемента
- собираем обратно через pyteomics.proforma.to_proforma

Образец см. в парсере PLGS, там похожая логика: `dasmixer-core/src/dasmixer/api/inputs/peptides/PLGS.py`

## MzTab-based парсер CasaNovo

Также сразу реализуем парсер CasaNovo, который должен быть основан на MzTab-парсере, но реализовать другую логику работы с модифицерованной последоватлеьностью.

Специфика:
- Не имеет таблицы белков, не выводит белки, не содержит более одного образца одновременно.
- Не имеет столбца modifications
- Вместо последнего уже предоставляет ProForma в столбце `opt_global_cv_MS:1003169_proforma_peptidoform_sequence`

т.е. нет импорта белков и импорт modified sequence реализуется через отдельный столбец as is 

## Парсер Pi-PrimeNovo

Парсер максимально стандартный. Нюансов два:
- использует маппинг к сканам по title, описано выше
- последовательность может иметь хитрый формат: `BSPRPDSPHDC[+57.021]YC[+57.021]AK`
  - Где:
    - Модификации указываются массами в квадратных скобках, список замен ниже
    - `BS`, `BT`, `BY` - фосфорилирование S,T,Y соответственно, заменяется на `S[Phospho]`, `T[Phospho]`...
    - B перед любой другой аминокислотой - артефакт, можно удалить (но только если применено правило для S,T,Y)
- не возвращает каноническую последовательность, только модифицированную. Каноническую получаем из модифицированной после приведения к proforma через `''.join([x[0] for x in proforma.parse(modified_seq)[0]])`

Список замен помимо описанных выше BS/BT/BY:
```python
replaces = {
    # N-terminal
    '[+43.006-17.027]': '[Carbamyl][Ammonia-loss]-',
    '[+42.011]':       '[Acetyl]-',
    '[+43.006]':        '[Carbamyl]-',
    '[-17.027]':        '[Ammonia-loss]-',
    # Аминокислотные
    '[+57.021]':       '[Carbamidomethyl]',
    '[+15.995]':       '[Oxidation]',
    '[+0.984]':        '[Deamidated]'
}
```

сепаратор в файле - `\t` (.tsv-файл)

Мэппинг полей:
- label -> преобразуется в title для сопоставления со спектром
- prediction -> sequence (требует описанного выше преобразования)
- score -> тут всё очевидно. Может быть в экспоненциальном формате, не должно быть проблемой для pandas

В файле также есть столбец charge, его игнорируем.
